# interaction-spec — 画布交互规格

> **产品规格，不是实现方案。** 规定「用户怎么操作、看到什么反馈」，不规定用什么技术手段。
> 两个渲染器都必须照此实现，**不许各自发挥**——各自发挥造成的差异是「没对齐规格」，
> 不是「渲染方案差异」，会污染选型结论。
>
> 基准：Figma / 即梦 / liblib canvas 这类画布工具的通用交互习惯。这些是行业约定，
> 用户已有肌肉记忆，**不要创新**。
>
> 范围：P2 实现。契约见 `docs/architecture.md` §11。

---

## 1. 视口（无限画布）

| 操作 | 触发 | 行为 |
|---|---|---|
| 平移 | **滚轮** | **垂直平移**（不是缩放） |
| 平移 | `Shift` + 滚轮 | 水平平移 |
| 平移 | **触控板双指滑动** | 按方向平移——与滚轮是同一个 `wheel` 事件，**无需区分设备** |
| 平移 | **中键按住拖拽** | 1:1 跟手 |
| 平移 | **空格按住 + 左键拖拽** | 同上（供没有中键的设备） |
| 缩放 | **`Ctrl` / `Cmd` + 滚轮** | **以光标位置为锚点**缩放 |
| 缩放 | **触控板捏合** | 同上——浏览器把捏合合成为 `ctrlKey === true` 的 `wheel`，**天然落入上一条** |
| 缩放 | `Ctrl` + `=` / `Ctrl` + `-` | 以视口中心为锚点，步进一档 |
| 适应内容 | `Shift` + `1` | 缩放到刚好容纳全部节点，四周留 5% 边距 |
| 实际大小 | `Ctrl` + `0` | 缩放回 100%，居中于内容 |

### 硬性规则

- **锚点缩放的定义**：缩放前后，**光标下的那个画布点必须停在原处**。这是「以光标为锚点」的唯一正确解释，也是最容易实现错的地方——错了的表现是画布会往光标反方向滑走。
- **缩放范围 `10%` – `400%`**。超出范围的输入被钳制，不是拒绝。
  - 不做 Figma 那种 1%–1600%：本项目是生成结果编排器，不需要看单个像素，也不需要俯瞰上万节点。
- **缩放步进按倍率，不按加法**：每格滚轮 `× 1.1` 或 `÷ 1.1`。线性加减会让放大时太慢、缩小时太快。
- **🔴 滚轮 = 平移，`Ctrl`/`Cmd` + 滚轮 = 缩放**（Figma 方案）。用户 2026-08-03 拍板。
  - **技术前提**：浏览器**无法可靠区分「鼠标滚轮」与「触控板双指纵向滑动」**——两者都是 `deltaMode: 0` 的 `wheel` 事件。因此「纯滚轮=缩放 + 双指=平移」这个组合**在技术上不成立**，只能靠启发式猜设备。
  - **本方案不需要任何启发式**：滚轮与双指都走平移、走同一条规则；`Ctrl`+滚轮与触控板捏合都走缩放、也走同一条规则（浏览器把捏合合成为 `ctrlKey === true` 的 wheel）。**两条规则各自覆盖两种设备，零判别。**
  - **对本项目尤其重要**：启发式若在两个渲染器里实现得不完全一致，会直接污染选型对照结论——那是我们最不能要的东西。
  - 连带要求：`wheel` 监听必须 `{ passive: false }` 且 `preventDefault()`，否则页面会跟着滚动。
- **无限画布**：视口没有边界限制，可以平移到任意远处。但要提供 `Shift+1` 让用户能回到内容。

## 2. 选择

| 操作 | 触发 | 行为 |
|---|---|---|
| 单选 | 左键点击业务单元 | 替换选中集为该单元 |
| 增选 / 减选 | `Shift` + 左键点击 | 在选中集里切换该单元 |
| 框选 | **左键在空白处按下并拖拽** | 选中与选框**相交**的全部业务单元 |
| 框选增选 | `Shift` + 左键框选 | 把框中的并入现有选中集 |
| 全选 | `Ctrl` + `A` | 选中当前画板下全部业务单元 |
| 取消选中 | 左键点击空白 / `Esc` | 清空选中集 |

### 硬性规则

- **框选判定用「相交」不用「完全包含」**。这是 Figma 与绝大多数画布工具的行为，用户预期如此——要求完全框住会让大对象几乎选不中。
- **框选的起点决定行为**：起点落在**空白**→ 框选；起点落在**已选中的单元**→ 拖拽移动；起点落在**未选中的单元**→ 先选中它，再拖拽。这三种必须分清，是最容易做错的地方。
- **选中粒度恒为业务单元**，永不选中业务单元内部的元素（内部元素本就不在 node 树里，见 `docs/domain.md` §2.2）。
- **锁定（`locked`）的节点不参与点选与框选**，但仍然渲染。

## 3. 移动与尺寸

| 操作 | 触发 | 行为 |
|---|---|---|
| 拖拽移动 | 左键拖住已选中的单元 | 选中集**整体**移动，1:1 跟手 |
| 微调 | 方向键 | 移动 1px |
| 快速微调 | `Shift` + 方向键 | 移动 10px |
| 等比缩放 | 拖拽选中框的**四角**控制点 | 等比改变尺寸 |
| 删除 | `Delete` / `Backspace` | 删除选中集 |

### 硬性规则

- **🔴 首版只允许单选缩放**（2026-08-04 裁定）。多选时**展示整个选中集的包围框**（视觉反馈），**但不提供控制点**。
  - **为什么砍**：多选整体等比缩放要求「把包围框的统一缩放映射回多个节点」——跨父级、父子同选去重、locked 排除、父相对坐标换算，复杂度不小，而它**对选型结论零贡献**（两侧都是同一个 core 函数 + 各自画控制点）。
  - 过 `AGENTS.md` §1.1 的判据：**它不是「生成 → 摆放 → 再生成」循环的必需品**，是排版矢量图形的设计器倾向功能。与当初砍掉 clipboard / contextMenu 同一条线。
  - 真需要时再补：core 加一个 `resizeProportionalMulti`，两侧各接一次即可，不会返工。
- **🔴 节点最小尺寸 = 32 画布 px**（宽高分别钳制）。定成 core 常量 `MIN_NODE_SIZE`，**两侧 import，不许各自取值**——这正是 `k` 公式与锚点提取必须收进 core 的同款风险。
  - 取 32 的理由：四角控制点视觉尺寸约 8px，节点缩到 32px 时四个点之间仍留有可拖的间隙；再小控制点就会重叠、没法操作。
- **🔴 只给四角控制点，不给边中点控制点——生成结果不允许被自由拉伸变形。**
  一张 AI 生成的图被拉成椭圆是产品事故，不是功能。要改比例只能重新生成。这一条是产品判断，不是技术限制。
- **拖拽过程是纯呈现**：移动预览由渲染器自己画，**不更新 node 树**。只在**松手时**提交一次 `onNodesMove`。
  逐帧提交会让一次拖拽产生几百条撤销日志（`docs/domain.md` §4.5）。
- **多选整体移动**：拖任意一个，整个选中集一起动，相对位置不变。

## 4. 其它

| 操作 | 触发 | 行为 |
|---|---|---|
| 激活 | 双击业务单元 | 打开该单元的生成参数面板 |
| 撤销 | `Ctrl` + `Z` | 见 `docs/domain.md` §4.5（持久化） |
| 重做 | `Ctrl` + `Shift` + `Z` | 同上 |

**不做**（`AGENTS.md` §1.1 主要矛盾）：右键菜单、剪贴板复制粘贴、对齐分布面板、图层面板拖拽排序、旋转控制点。

## 5. 视觉反馈

### 光标

| 状态 | 光标 |
|---|---|
| 空白处 | `default` |
| 中键按下 / 空格按下 | `grabbing` |
| 空格按住未拖动 | `grab` |
| hover 业务单元 | `move` |
| hover 四角控制点 | `nwse-resize` / `nesw-resize` |
| 框选进行中 | `crosshair` |

### 状态样式

| 状态 | 表现 |
|---|---|
| hover | 1px 淡色描边 |
| 选中（单个） | 2px 强调色描边 + 四角控制点 |
| 选中（多个） | 每个单元 2px 描边；**整个选中集外再套一个包围框**，控制点只出现在包围框上 |
| 框选框 | 半透明填充 + 1px 实线边 |

### 硬性规则

- **描边与控制点不随画布缩放而变粗变细**——缩放到 400% 时选中框仍是 2px 视觉宽度。这需要按 `1 / viewport.scale` 反向补偿，两侧都要做，是个常见坑。
- **控制点的尺寸同理**，恒为固定的视觉像素。

### 6.1 连线 = 溯源关系，不是节点图

> ~~初版曾把「连线」读成 ComfyUI 那类**执行流节点图**（节点是算子、连线决定执行顺序与数据传递）。
> **这是过度解读，已被用户 2026-08-03 当场推翻，保留原文以志错。**~~

**用户原话**：*「是无限画布，只不过这个连线是——比如图片后面出 abc 版本三个视频，那么连线就是说这三个视频的来源都是这张图片。」*

所以：

> **它仍然是无限画布。连线表示「派生自」——记录一个生成结果是从哪个节点来的。**
> 「离群节点」= 既没有来源、也不是任何节点的来源的孤立生成单元。

**这个差别决定了成本量级**：

| | 执行流节点图（我的误读） | 溯源关系（实际） |
|---|---|---|
| 边的含义 | 数据流向，决定执行 | **记录来源，事后可查** |
| 需要的模型 | 独立 Edge 实体、拓扑排序、环检测、端口类型 | **生成单元上加一个 `sourceFwIds: string[]`** |
| 影响面 | schema / 持久化 / 执行引擎 / 命中测试 全线 | 一个字段 + 一层连线渲染 |

模型设计见 `docs/domain.md` §3.2.2。

### 6.1.2 🔴 视频节点内嵌可播放播放器 —— 可能是选型的决定性差异

图中「视频节点 13」**内嵌了一个真实可用的播放器**：播放/暂停按钮、进度条、`0:01 / 0:05` 时间、音量、截图按钮，且进度条处于播放中的位置。

**这不是显示首帧，是真的在画布上播视频。** 而这一项在两个渲染方案上的代价差距极大：

| | `renderer-dom` | `renderer-leafer` |
|---|---|---|
| 播放器本体 | 一个 `<video>` 标签，浏览器原生控件或自绘 | Canvas 里没有 `<video>`。要么把视频帧当纹理逐帧绘制，要么在 canvas 上方叠一层 DOM |
| 播放控件 | HTML 元素，直接可用 | **进度条、按钮、音量全部要自己画 + 自己做命中测试** |
| 多个视频同时播 | 浏览器管理 | 逐帧取纹理上传，性能与内存都要自己扛 |

**这大概率是整个选型里成本差距最大的一项**，比帧率数字更能决定结论。已写进 `docs/architecture.md` §8.2 作为必测项——**不要等到 P3 才发现**。

### 6.2 「分镜组」不是设计器的「分组」

本规格 §5.1 曾把「组件 / 变体 / 分组」列为通用设计器功能砍掉。参考方案里的「**合并分镜组**」推翻了这个定性的一部分：

**分镜（shot）是影视创作的基本单位**，不是「把几个图形捆一起方便一起挪」。它服务的是「生成 → 摆放 → 再生成」循环，按 `AGENTS.md` §1.1 的判据**应该做**。

⚠️ 待重新定性，同样登记为开环，本次不改。

## 附录 A · 视频节点与原生控件的指针冲突（2026-08-05 裁定）

### 问题

DOM 侧用原生 `<video controls>` 后，`codex-dom-video` 实测发现：UA shadow tree 的指针事件会
重定向到 `<video>` 宿主，而画布监听器把宿主当节点 —— **拖进度条超过 4px 会同时拖动整个节点**。

它的止血方案是 `data-fw-interaction="ignore"`，保证控件可操作；**代价是点视频本体不能选中/拖动节点**。
它没有自行决定产品语义就停下上报，这是对的。

### 裁定：画布优先，播放次之，用「激活」区分

| 状态 | 单击 | 拖动 | 播放控件 |
|---|---|---|---|
| **未激活**（默认） | 选中节点 | 移动节点 | **不接管指针** |
| **已激活**（双击进入，或选中后再单击） | 操作控件 | 拖进度条 | **接管指针** |
| 点画布空白 | 退出激活 | — | — |

**依据**：对标产品（即梦 / liblib）里，画布上的视频**首先是一个可摆放的素材**，其次才是可播放的媒体。
用户在画布上最高频的动作是选中、移动、连线、再生成，不是拖进度条。
把播放控件设为「需要显式进入」既解决了冲突，也没有牺牲主链路。

这与 Figma 对待嵌入内容的做法一致：默认当作一个对象，双击才进入其内部交互。

### 🔴 这条同时是选型证据

DOM 侧「一个 `controls` 属性白送整套播放器」看起来完胜 Leafer 的自绘，
**但这次冲突暴露了隐藏代价：白送的控件同时夺走了命中测试的控制权。**

浏览器无法可靠区分用户点的是画面还是封闭 shadow tree 里的控制条，
所以我们只能在「控件能用」和「节点能选」之间二选一，靠额外的激活态绕开。

Leafer 侧自绘控件要写更多代码，**但命中测试完全在自己手里，不存在这个冲突**。

**结论：DOM 的视频节点不是「零成本」，是「零绘制成本 + 一笔交互控制权的代价」。**
成本表里要如实体现这一点，不能只记「28 行代码」。

## 附录 B · 节点 hover 业务工具条（2026-08-05 裁定四条空档）

`codex-dom-video` 实现 G4-3 后上报四条规格空档并拒绝自行拍板，均已裁定如下。
**两侧渲染器都按此对齐。**

### B.1 动作字符串 —— 🔴 删除不走 `onNodeAction`

| 按钮 | 通道 |
|---|---|
| 重新生成 | `onNodeAction(fwId, 'regenerate')` |
| 下载 | `onNodeAction(fwId, 'download')` |
| **删除** | **`onNodesDelete([fwId])`** —— 既有专用通道 |

三个「生成」语义分开，不要合并：
`generate`（空态首次）/ `retry`（失败后重试同参）/ `regenerate`（已成功，再来一次）。

**删除为什么必须单独走**：撤销所需的 `inboundRefs` 对称持有逻辑挂在 `onNodesDelete`
那条路径上（`domain.md` §4.5）。开第二条删除路径，必然导致「从工具条删」和
「按 `Delete` 删」的撤销行为不一致 —— **而这类分叉最难被测试发现**，
因为两条路径各自的测试都会是绿的。

### B.2 状态可用性 —— 渲染器按节点自身状态决定禁用

执行方顾虑「不在渲染器内复制业务规则」，方向对，但**这一条不算复制业务规则**：
渲染器本来就要渲染四态，按状态决定按钮 enabled/disabled 是**渲染状态**，不是判断业务。
动作真正做什么仍然由 host 决定。

| 节点状态 | 生成类按钮 | 下载 | 删除 |
|---|---|---|---|
| `empty` | `generate` 可用 | **禁用**（没有产物） | 可用 |
| `pending` / `running` | **禁用**（正在跑） | **禁用** | 可用 |
| `succeeded` | `regenerate` 可用 | 可用 | 可用 |
| `failed` | `retry` 可用 | **禁用** | 可用 |

禁用要有可见的禁用态，不许「点了没反应」。

### B.3 与视频激活态的边界

**同一节点进入激活态时，它的工具条隐藏。**

依据：激活的含义就是「进入该节点的内部交互」，此时外部操作应当让位 —— 这与附录 A
「画布优先 + 激活态」是同一条原则的两面。当前 `ai-image`/`ai-video` 与纯素材 `video`
尚无重叠，但规则先钉死，避免以后两侧各猜一套。

### B.4 坐标语义 —— 🔴 固定屏幕像素，始终水平

工具条**不随视口缩放变大、不随节点旋转**。

依据与既有的 `1/scale` 描边补偿完全一致：**它是 UI 附件，不是画布内容。**
内容跟随变换，操作它的把手不跟随 —— 缩放到 30% 时工具条跟着缩成看不清、
节点旋转 45° 时按钮也歪着，都是错的。

两侧都要这样。若实现上需要提到根级 overlay，那就提，**但两侧必须同时改，不许一边一套**。
