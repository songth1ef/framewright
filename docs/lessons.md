## 已验证决策

### 1. 项目归属先定，再谈开源（2026-08-03）

**结论**：动手前先把「这是个人作品还是雇主交付」问清楚，再决定开不开源。

**为什么**：本项目的业务灵感来自作者工作场景，但归属定为**个人作品 / 技术预研**。归属一旦模糊，后面每个决定都会被污染——代码能不能公开、要不要老板点头、算不算个人作品切片，全悬着。定死归属后，四条硬约束（不含雇主源码接口文案、demo 数据中立、provider 可替换、依赖 license 可商用）才有依据。

**怎么用**：见 `AGENTS.md` §2。任何一次提交都要过这四条。

### 2. 双实现验证的前提是「不让任一侧偷跑」（2026-08-03）

**结论**：要用两套实现做选型对照，架构上必须先保证它们**被公平对待**。

**为什么**：最容易毁掉对照实验的做法是让状态渗进渲染器——比如把选中态存在 Leafer 节点上，或者让 DOM 侧直接吃 React 的 diff。一旦发生，测出来的差异是架构差异不是渲染方案差异，结论作废。

**怎么用**：node 树是唯一真相源；渲染器永不直接改树，只上报意图；`core` 零渲染依赖；上层不写渲染器品牌分支。见 `docs/architecture.md` §2–3。

### 3. 「验证选型」≠「两套全功能产品线」（2026-08-03）

**结论**：双渲染器并行只做**最小元素集**（frame / box / img / video 四个），不是两条完整产品线。

**为什么**：四个元素已经覆盖了容器嵌套、坐标累加、裁剪、图形绘制、外部素材加载、媒体播放——足够暴露两个渲染方案的真实差异。再多加元素只增加成本、不增加信息量。

**怎么用**：新增元素类型前先问「它能让选型结论改变吗」，不能就不加。

### 4. 「不知道哪个更好」应该做成可切换，而不是先选一个（2026-08-03）

**结论**：渲染层做成**可插拔 + 运行时一键切换**，两版功能同步开发；不做构建期二选一，也不做「先做完一个再做另一个」。

**为什么**：作者事先无法判断 DOM 与 LeaferJS 哪个更适合 AI 画布，纸面推演给不出答案。做成运行时可切换有三重收益，超出「架构优雅」的范畴：

1. **它是验收装置**——同一份数据、同一串操作，切一下就能现场对比，比任何 benchmark 报告都直观。
2. **它是架构测试仪**——任何把状态偷偷塞进渲染器的写法，一切换就当场丢状态露馅。这条约束不用靠人 review 守，靠功能本身守。
3. **它保住了退路**——选型结论万一变了，换的是一个 adapter，不是整个应用。

**代价要认**：两个渲染器都是运行时依赖（包体积翻倍，可用懒加载缓解），且交互事件必须抽象到语义层（两套事件系统在事件层无法统一）。这个代价是**为了拿到结论而付的**，不是过度设计。

**怎么用**：`RendererAdapter` 三方法 `mount/update/destroy`；会话状态（视口/选中）一律在 core；见 `docs/conventions.md` §4。

### 5. 双实现的接口，必须由两个实现从两边夹出来（2026-08-03）

**结论**：P0 阶段两个渲染器**同时**写，但功能面压到最小（只静态渲染 frame + box，无交互）。不用「先做完一个再做第二个」。

**为什么**：只靠一个实现去定 `RendererAdapter`，定出来的接口必然偏向那一侧——先写 DOM 会漏掉 Leafer 的命中检测与坐标系差异，先写 Leafer 会漏掉 DOM 的事件冒泡与 CSS 布局假设。等第二个实现进来才发现接口不对，两边都要返工。功能面压到最小时，写两遍的成本最低、返工也最便宜，正是夹逼接口的最佳时机。

**怎么用**：见 `docs/architecture.md` §5.1 阶段排序。

### 6. 战线风险用排序化解，不靠自觉（2026-08-03）

**结论**：「双渲染器 + 完整后端 + 真实生成」三件事确定要做，但**串成 P0→P3 四阶段**，不并行。

**为什么**：作者已知的复发倾向是战线过长。这类风险靠「注意一点」是防不住的——决定要做的事不会因为提醒而变少。可行的做法是把并行改成串行，让每个阶段有独立的完成信号（P0 = 接口稳定；P1 = 刷新后数据还在；P2 = 切换后状态不丢；P3 = 真素材落回画布）。

**怎么用**：新任务开工前先问「它属于哪个阶段」，不属于当前阶段就记进 backlog 不做。

### 7. 两侧的能力不对称，是结论本身，不是要抹平的差异（2026-08-03）

**结论**：LeaferJS 有现成生态（`leafer-editor` 提供选中框/变换/辅助线吸附等），DOM 侧多半要手写。**这个差距要如实量出来记进「实现成本对照表」，而不是想办法让它看不出来。**

**为什么**：本项目要回答的是「做 AI 画布该用哪个方案」。对一个真实项目来说，「这个功能装个插件 2 小时 vs 手写 2 天」比「帧率 58 还是 60」更能决定选谁。如果为了「公平」而在两侧都手写、或者只对比性能不对比开发成本，反而丢掉了最有决策价值的信息。

**注意区分两件事**：功能**要**同步实现（否则体验对比不公平），但实现**成本**要如实记差（那是结论）。两者不矛盾。

**怎么用**：见 `docs/architecture.md` §8.2。每个功能两侧各记一行，耗时含踩坑返工；一侧做不到就写清技术原因——那是最值钱的条目。

### 8. 选型决定要做成可逆的（2026-08-03）

**结论**：后端选 Next.js 全栈，但业务逻辑全部收进 `@framewright/server-core`（纯 TS、零 Next 依赖），Route Handler 只是薄适配层。

**为什么**：「Next.js 还是 NestJS」在当前信息下答案清楚（后端职责薄、风险全在前端双渲染器、同路径已跑通过一次），但未来条件可能变（真要做实时协作或队列）。与其反复纠结，不如**把选择做成可逆的**——分层一到位，将来搬 `server-core` + 重写适配层即可，业务逻辑一行不改。

**推广**：凡是「现在信息不足、但拖着不定更亏」的技术选型，优先找一个能把决定变可逆的分层，然后果断定，别悬着。

**重评触发条件**（达成前不重开此议题）：要多人实时协作 / 要自跑队列长任务 / 后端要被多个不同前端复用。

### 9. 双渲染器真正要写两遍的，只有「命中 + 绘制」（2026-08-03）

**结论**：undo/redo、图层操作、剪贴板、右键菜单、对齐分布、**吸附与辅助线的几何计算**——这些全是纯数据/纯几何，放 `core` 只写一遍，两个渲染器共享。要写两遍的只有命中测试、实际绘制、事件绑定。

**为什么**：这个判断不是推的，是量的——实测 gzm-design 的 `views/Editor` 目录下全部 `.ts`，**只有 8 个文件 import vue**，服务层几乎全是纯 TS。一个成熟的 Vue 画布编辑器能做到服务层与框架解耦，说明这条分界线是真实存在的，不是理论上的理想分层。

**含义**：双渲染器的成本远低于直觉。「Leafer 有插件、HTML 要手写」这个担忧，大头落在可共享的那一半。

**怎么用**：新增功能先问「它需要知道自己被画在 DOM 还是 Canvas 上吗」——不需要就进 `core`。见 `docs/architecture.md` §9.2。

### 10. 营销文案不是许可条款（2026-08-03）

**结论**：判断能不能用一个开源项目，只看 `LICENSE` 文件原文，且核实两个独立来源。

**为什么**：gzm-design 官网写「免费开源、免费可商用」，同时卖 4299 的专业版——**这种「开源版 + 付费专业版」双轨结构，正是最常用 GPL/AGPL 来逼商用付费的形态**，营销页的「可商用」完全可能只指开源版在 GPL 条件下的商用。本次核实结果是真 MIT（Gitee 的 LICENSE 原文 + GitHub 镜像 `LvHuaiSheng/gzm-design` 双源一致），但**这个结论是查出来的，不是从文案信出来的**——换一个项目，同样的文案可能对应完全不同的条款。

**怎么用**：见 `AGENTS.md` §5。另：MIT 的唯一实质义务是**保留版权与许可声明**，这条要落成 `THIRD-PARTY-NOTICES.md` + 文件头注释，不能只是「知道了」。

### 11. 字段前缀能表达归属，但挡不住冲突（2026-08-03）

**结论**：node schema 的语义字段用 `fw` 前缀（`fwId` / `fwType`），**但真正防冲突的是「禁止整体展开」这条铁律**，不是前缀。

**为什么**：给 `id` / `type` 加前缀的直接收益是**可读性**——代码里同时出现 framewright 的 node 和渲染器的节点时，`fwId` 一眼可辨归属，不用回头查类型。但它防不住冲突：LeaferJS 的节点属性 `x` `y` `width` `height` `rotation` `opacity` `visible` `name` `children` 与我们的字段**全部同名**，只前缀两个反而制造「其余安全」的错觉。

**真正的防线**：逐字段显式映射，禁止 `new Rect({...node})` 这类展开。这样新增字段不会自动泄漏进渲染器，改名会在编译期报错而不是在运行时变成「莫名其妙渲染不对」——后者在双渲染器项目里还会两侧表现不一致，是最难查的一类 bug。

**推广**：命名约定解决的是**人读代码**的问题，别指望它解决**机器行为**的问题；后者要靠类型系统或显式屏障。

**怎么用**：见 `docs/domain.md` §3.1.1 与 §3.3 规则 7。

### 12. 把纪律变成机器可检查的约束（2026-08-03）

**结论**：`core` 导出 `SHAPE_TYPES` 全集，两个渲染器的 shape 注册表必须覆盖全集，缺任何一个在装载时直接报错。

**为什么**：「两版同步开发、不许单侧先行」原本只是 `conventions.md` 里的一条纪律——纪律靠人自觉，而人在赶进度时最先放弃的就是自觉。注册表完整性检查把它变成「加一个 shape 不两边都加就跑不起来」的硬约束。

**推广**：**每写下一条「必须记得……」的纪律，都先想一下有没有办法让机器替你记。** 本仓已有两例：注册表完整性检查（守两版同步）、切换测试（守状态不渗进渲染器）。想不出机器办法的才留成纪律。

**注意**：允许一侧显式注册「不支持」实现（渲染占位 + 上报），而不是留空——这样「做不到」是被记录的，正好喂给 §8.2 实现成本对照表。

### 13. shape 不可能在两个渲染器间 1:1 对应（2026-08-03）

**结论**：自定义 shape 拆三段——数据（`node-schema.ts`）、纯逻辑（`core/shapes/`）、渲染绑定（两侧各写）。**只有第三段写两遍，而且很薄。**

**为什么**：gzm-design 的 `Image2` 注释直接写明它存在的理由是「解决官方 Image 元素不能在初始化时设置 fill 的 opacity 问题」——**一个纯粹的 Leafer workaround，DOM 侧根本没有这个问题**。这个例子说明：shape 层的差异不只是「实现方式不同」，而是**有些 shape 在另一侧压根不需要存在**。硬追求 1:1 对应反而是错的。

反过来，QR 码的 `QRCode.toString(text, opts) → SVG 字符串` 完全与渲染器无关，属于纯逻辑段，只写一遍。**判据：这段代码需要知道自己被画在 DOM 还是 Canvas 上吗？**

**怎么用**：见 `docs/architecture.md` §10。

### 14. 借鉴一个成熟项目时，最大的风险是继承它的目标（2026-08-03）

**结论**：gzm-design 是**通用设计器**，framewright 是**生成结果编排器**。借它的代码可以，借它的功能清单不行。

**为什么**：初版借鉴清单把 `clipboard` / `contextMenu` / `layer` 一并列为「借鉴逻辑落 core」，理由是「纯数据操作、渲染器无关」——技术判断没错，但**问错了问题**。该问的不是「这段代码能不能复用」，而是「这个功能我们要不要」。剪贴板、右键菜单、图层管理体系服务的是「把图形调得更好看」，那是设计器的目标，不是我们的。

**机制上为什么容易犯**：借鉴时人是在读对方的代码，对方代码组织得越好，越容易顺着它的结构想问题，于是**它的目标就随着它的架构一起被搬过来了**。这个漂移是无声的——每一步都合理，走完发现在做另一个产品。

**怎么用**：定一条**产品级判据**放在最高优先级文件里（本仓是 `AGENTS.md` §1.1「服务生成循环还是服务图形美化」），每个功能先过它，再谈技术可行性。**顺序不能反。** 本次按此重定性，借来的代码量从 ~1070 行降到 ~550 行。

### 15. 数据模型的粒度，由「用户选中什么」决定，不由「画出来是什么」决定（2026-08-03）

**结论**：node 树的粒度 = 用户选中的粒度 = 业务单元的粒度。一个 `ai-image` 是一个 node，它内部的图片本体、生成中遮罩、prompt 摘要条、hover 操作条**都不是 node**。

**为什么**：一开始按「视觉元素」建模（frame/box/img/video），看起来干净，但会引出一个假问题——「按 type 拆是不是太细了」。真正的拆分依据不是「有几种形状」，而是「有几种**用户会整体选中、整体移动、整体删除**的东西」。业务单元的种类天然很少，所以按它拆既不细也不粗。

**三个连锁好处**（这条规则的价值远超命名整洁）：

1. **命中测试天然正确**——不需要写逻辑去「抑制选中子元素」，因为子元素压根不在树里。
2. **`getRenderedBounds()` 报的就是选中框该画的位置**。
3. **⭐ 它让双渲染器同步变简单，不是变难**——parity 只需断言业务单元的**外框**一致，内部布局允许两侧各用最优解（DOM 用 flex，Leafer 用绝对定位）。约束反而放宽了。

**推广**：建模时先问「用户会把什么当成一个东西来操作」，再问「它长什么样」。顺序反了就会拆出一堆没人会单独操作的节点，然后再花力气把它们藏起来。

### 16. 交互的「计算」几乎全能进共享层（2026-08-03）

**结论**：无限画布的交互里，只有「监听手势」和「画出反馈」必须两侧各写；**坐标换算、锚点缩放、框选相交判定全是纯数学/纯几何，进 `core` 只写一遍**。

**为什么**：这是 #9 那条规律在交互上的应用，而且更彻底。直觉上交互是最「渲染器相关」的部分——DOM 有事件冒泡与 CSS 命中测试，Leafer 有自己的事件系统与命中检测。但把一次交互拆开看，真正依赖渲染方式的只有两端（收输入、画反馈），中间那段全是数学。

**额外收益**：两个渲染器共享同一套几何，从根上杜绝「框选在 DOM 侧选中 5 个、Leafer 侧选中 4 个」这类分叉——这类 bug 靠测试很难覆盖全。

**怎么用**：见 `docs/architecture.md` §11.2。新写交互时先问「这一步需要知道自己被画在 DOM 还是 Canvas 上吗」。

### 17. 独立作答收敛 = 铁证；单侧独有 = 方法的价值（2026-08-03，T11 实证）

**结论**：让两个不同模型在**互不可见**的前提下评估同一份接口草案，产出的两份答案要分两类读——

| 类别 | 意味着什么 | 怎么处置 |
|---|---|---|
| **两侧独立收敛** | 铁证，不需要再论证 | 直接采纳 |
| **只有一侧提出** | 那一侧的技术处境独有 | 也要采纳，而且这是方法的全部价值所在 |

**实测数据**（T10 两份答案，DOM 由 Codex 写、Leafer 由 Kimi 写，互不可见）：

- **四项独立收敛**：`onNodesMove` 坐标系没钉、缺 `onNodesResize`/`onNodesDelete`、`onViewportChange` 频率未定义、「空白」判定语义空洞。其中第四项尤其说明问题——**两侧从完全不同的技术路径撞上了同一个语义空洞**（DOM 是「`closest()` 永远命中 root」，Leafer 是「无 fill 的 Box 命中语义不明」），同一个坑，两种长相。
- **三项单侧独有**：Leafer 内建手势直接改 transform（DOM 没有「内建手势」这种东西）、场景图打平的连带税（DOM 天然嵌套）、复合单元内部按钮冒泡需 `onNodeAction`（Leafer 内部元素自绘）。**这三条没有一条是两侧都能看到的**——同一个模型写两遍会同时缺席。

**⚠️ 但有一条我照单全收后被证伪，这本身是本条最重要的补充**：

Leafer 侧称「demo 文档的子节点恰好全在 root 直下，父相对坐标 == 绝对坐标，故 parity 测不出坐标系分歧，P0 是假绿」。我当场采信并写进了契约与本条。**随后读 `demo-document.ts` 原文，发现前提不成立**——`nested-box` 挂在偏移 `(380,60)` 的 `inner-frame` 下，父相对 `(20,20)` ≠ 绝对 `(400,80)`。

**由此得到一条比原结论更重要的区分**：

| 单侧提出的东西 | 可信度 | 处置 |
|---|---|---|
| **自己那一侧的技术处境**（我这边有什么 API、什么坑、什么做不到） | 高——它是那一侧唯一的在场者 | 直接采纳 |
| **关于共享代码/共享数据的事实断言** | 低——它可能记错、可能没重读 | **必须自己查原文** |

Leafer 侧关于 Leafer 内建手势的每一条都对（技术处境），关于 demo 文档内容的那一条是错的（共享代码的事实断言）。**这两类混在同一份高质量答案里，很容易一起被采信。**

**推广**：交叉验证解决的是「有没有想到」的问题，解决不了「记没记对」的问题。**凡是可以打开文件核对的断言，就去打开文件**——尤其当它读起来像个惊悚发现的时候。

（原结论「坐标系语义必须钉死」仍然成立且已定案，只是那条论据是错的。）

### 18. 依赖 license 要在引入前核实，不是事后补（2026-08-03）

**结论**：每个依赖引入前登记 license，GPL / AGPL / SSPL 默认拒绝。

**为什么**：本仓暂定开源，但不排除未来把内核并进闭源商用产品。传染性许可会锁死这条路，而依赖一旦长进核心层，替换成本远高于当初换一个。「抄开源项目」时抄思路免费、抄代码受约束。

**怎么用**：`docs/architecture.md` §6 依赖表，每次 `pnpm add` 同步登记。

## 踩坑记录

### 1. leafer-ui 在 vitest 下 import 即崩，需桩 canvas API（2026-08-04，C1-leafer）

**现象**：`import 'leafer-ui'` 在 node/jsdom 环境直接抛 `CanvasRenderingContext2D is not defined`（后续还有 `Path2D` / `DragEvent` / `getContext` 返回 null）。

**结论**：leafer-ui 的 web 平台层在**模块加载时**就触碰浏览器 canvas API。要在单测里构造并检查 leafer 对象树（结构、属性、事件接线），先执行 `packages/renderer-leafer/src/leafer-test-stub.ts`（桩 `CanvasRenderingContext2D` / `Path2D` / `DragEvent` + 全 no-op 的假 2d context），且它必须是测试文件的**第一个 import**（ES 模块按 import 顺序求值）。

**边界**：桩环境下不做任何真实渲染，几何与像素断言归 e2e（真实浏览器）。用 `// @vitest-environment jsdom` 提供 window/document。

### 2. leafer 的 `scaleFixed` 对 `strokeWidth` 不生效（2026-08-04 实测，leafer-ui 2.2.9）

**实测**：`strokeWidth: 10` 的 Rect，scale=4（分别挂在 Leafer 根与 Group 上两种配置），`scaleFixed: true` 与否描边视觉厚度都是 40px——**没有任何补偿**。源码佐证：`UIRender.ts` 里只有 `shadow.scaleFixed` 被读取，元素自身的 `scaleFixed` 不参与描边补偿。

**结论**：「描边宽度不随缩放变粗」必须手写 `strokeWidth / viewport.scale` 反向补偿（连线层已这么做）。**D5 选中 overlay 同此**；且现有 frame/box 的选中描边（2px）目前会随缩放变粗，属 D5 要处理的已知项。

### 3. root frame 的 background 是画布底色，会盖住先于它 add 的层（2026-08-04，C2-leafer）

**现象**：溯源连线层 `leafer.add(连线层)` 先于 root frame，结果连线完全不可见——root 的白色 background 画在整个 800×450 上，把它盖住了。

**结论**：「画在所有节点之下」的正确落点是**root frame 内部、作为第一个孩子**——在 root 自己的 background 之上、一切业务节点之下。后续的选中 overlay（D5）若也要「压在所有节点之上」，镜像地应作为 root 的**最后**一个孩子，而不是 add 到 leafer 根。

> 补注（2026-08-04，D5-leafer 实施）：overlay 实际落在 **leafer 根上、root frame 之后** add——
> 绘制顺序等价（在所有节点之上），但坐标保持画布绝对坐标（与 DOM 侧 overlay 同口径），
> 不必减 root 原点。两种落点都成立，选坐标语义更简单的那个。

### 4. Leafer 命中探针的三个实测要点（2026-08-04，D2/D5-leafer）

**背景**：D2-leafer 用 `leafer.selector.getByPoint` 做命中探针（等价 DOM 侧的 `closest()`），实测结论：

1. **坐标系**：入参是 view 相对坐标（与 Leafer 事件的 x/y 同系，`clientX - viewBounds`），不是画布坐标——命中内部走 `__world` 变换，已含 host 设置的 `leafer.x/y/scale`（viewport），无需自己换算。
2. **调用前先 `updateLayout()`**：draw() 重建场景图后、渲染帧之前到达的命中会拿到过期包围盒（`Interaction.findPath` 对模拟交互同样这么做）。
3. **🔴 overlay 层不能整层 `hittable: false`**：`worldHittable` 沿父链逐级检查，父层 false 会把子元素全部打成不可命中——缩放控制点就点不到了。正确做法：层用 `Group`（非 branchLeaf，永不自命中），装饰元素（框选框/描边）逐个 `hittable: false`，控制点保持可命中。

**桩环境边界**（接踩坑 1）：jsdom 桩下 `measureText` 返回 0 宽，**Text 元素命中不可靠**；Rect 经 hitCanvas 的命中在桩下恒真（假 2d context 全 truthy）。所以命中类单测只断言 data 标记与结构，真实命中判定归 e2e（真实浏览器）。

### 5. pnpm workspace 的服务端外部包必须从 Next app 可解析（2026-08-06）

**现象**：`server-core` 静态引入 `@prisma/adapter-libsql` 后，Next 把它的 Node 入口打进 webpack，进而把 libSQL 依赖里的 README / LICENSE 当 JavaScript 解析，生产构建失败。只加 `serverExternalPackages` 不够；手工 external 后虽能编译，但 trace 不包含 adapter，部署运行时会缺包。

**结论**：workspace 源码包由 Next 转译、且其中的 Node 依赖要 external 时，该依赖还必须是 Next app 的直接运行时依赖。这样 webpack 能保留 Node `require`，文件追踪也能从 app 的 `node_modules` 入口收集 adapter、传递依赖与原生文件。

**本次落地**：`@prisma/adapter-libsql@6.19.3` 同时声明在 `server-core`（模块所有权）与 `apps/web`（部署可解析性）；`next.config.ts` 将它列入服务端外部包并保留为 CommonJS external。Linux Node 22 干净构建已验证 trace 同时包含 libSQL adapter 与 `better_sqlite3.node`。
