## 已验证决策

### 1. 项目归属先定，再谈开源（2026-08-03）

**结论**：动手前先把「这是个人作品还是雇主交付」问清楚，再决定开不开源。

**为什么**：本项目的业务灵感来自作者工作场景，但归属定为**个人作品 / 技术预研**。归属一旦模糊，后面每个决定都会被污染——代码能不能公开、要不要老板点头、算不算个人作品切片，全悬着。定死归属后，四条硬约束（不含雇主源码接口文案、demo 数据中立、provider 可替换、依赖 license 可商用）才有依据。

**怎么用**：见 `AGENT.md` §2。任何一次提交都要过这四条。

### 2. 双实现验证的前提是「不让任一侧偷跑」（2026-08-03）

**结论**：要用两套实现做选型对照，架构上必须先保证它们**被公平对待**。

**为什么**：最容易毁掉对照实验的做法是让状态渗进渲染器——比如把选中态存在 Leafer 节点上，或者让 DOM 侧直接吃 React 的 diff。一旦发生，测出来的差异是架构差异不是渲染方案差异，结论作废。

**怎么用**：node 树是唯一真相源；渲染器永不直接改树，只上报意图；`core` 零渲染依赖；上层不写渲染器品牌分支。见 `docs/architecture.md` §2–3。

### 3. 「验证选型」≠「两套全功能产品线」（2026-08-03）

**结论**：双渲染器并行只做**最小元素集**（frame / box / img / video 四个），不是两条完整产品线。

**为什么**：四个元素已经覆盖了容器嵌套、坐标累加、裁剪、图形绘制、外部素材加载、媒体播放——足够暴露两个渲染方案的真实差异。再多加元素只增加成本、不增加信息量。

**怎么用**：新增元素类型前先问「它能让选型结论改变吗」，不能就不加。

### 4. 「不知道哪个更好」应该做成可切换，而不是先选一个（2026-08-03）

**结论**：渲染层做成**可插拔 + 运行时一键切换**，两版功能同步开发；不做构建期二选一，也不做「先做完一个再做另一个」。

**为什么**：作者事先无法判断 DOM 与 LeaferJS 哪个更适合 AI 画布，纸面推演给不出答案。做成运行时可切换有三重收益，超出「架构优雅」的范畴：

1. **它是验收装置**——同一份数据、同一串操作，切一下就能现场对比，比任何 benchmark 报告都直观。
2. **它是架构测试仪**——任何把状态偷偷塞进渲染器的写法，一切换就当场丢状态露馅。这条约束不用靠人 review 守，靠功能本身守。
3. **它保住了退路**——选型结论万一变了，换的是一个 adapter，不是整个应用。

**代价要认**：两个渲染器都是运行时依赖（包体积翻倍，可用懒加载缓解），且交互事件必须抽象到语义层（两套事件系统在事件层无法统一）。这个代价是**为了拿到结论而付的**，不是过度设计。

**怎么用**：`RendererAdapter` 三方法 `mount/update/destroy`；会话状态（视口/选中）一律在 core；见 `docs/conventions.md` §4。

### 5. 双实现的接口，必须由两个实现从两边夹出来（2026-08-03）

**结论**：P0 阶段两个渲染器**同时**写，但功能面压到最小（只静态渲染 frame + box，无交互）。不用「先做完一个再做第二个」。

**为什么**：只靠一个实现去定 `RendererAdapter`，定出来的接口必然偏向那一侧——先写 DOM 会漏掉 Leafer 的命中检测与坐标系差异，先写 Leafer 会漏掉 DOM 的事件冒泡与 CSS 布局假设。等第二个实现进来才发现接口不对，两边都要返工。功能面压到最小时，写两遍的成本最低、返工也最便宜，正是夹逼接口的最佳时机。

**怎么用**：见 `docs/architecture.md` §5.1 阶段排序。

### 6. 战线风险用排序化解，不靠自觉（2026-08-03）

**结论**：「双渲染器 + 完整后端 + 真实生成」三件事确定要做，但**串成 P0→P3 四阶段**，不并行。

**为什么**：作者已知的复发倾向是战线过长。这类风险靠「注意一点」是防不住的——决定要做的事不会因为提醒而变少。可行的做法是把并行改成串行，让每个阶段有独立的完成信号（P0 = 接口稳定；P1 = 刷新后数据还在；P2 = 切换后状态不丢；P3 = 真素材落回画布）。

**怎么用**：新任务开工前先问「它属于哪个阶段」，不属于当前阶段就记进 backlog 不做。

### 7. 两侧的能力不对称，是结论本身，不是要抹平的差异（2026-08-03）

**结论**：LeaferJS 有现成生态（`leafer-editor` 提供选中框/变换/辅助线吸附等），DOM 侧多半要手写。**这个差距要如实量出来记进「实现成本对照表」，而不是想办法让它看不出来。**

**为什么**：本项目要回答的是「做 AI 画布该用哪个方案」。对一个真实项目来说，「这个功能装个插件 2 小时 vs 手写 2 天」比「帧率 58 还是 60」更能决定选谁。如果为了「公平」而在两侧都手写、或者只对比性能不对比开发成本，反而丢掉了最有决策价值的信息。

**注意区分两件事**：功能**要**同步实现（否则体验对比不公平），但实现**成本**要如实记差（那是结论）。两者不矛盾。

**怎么用**：见 `docs/architecture.md` §8.2。每个功能两侧各记一行，耗时含踩坑返工；一侧做不到就写清技术原因——那是最值钱的条目。

### 8. 选型决定要做成可逆的（2026-08-03）

**结论**：后端选 Next.js 全栈，但业务逻辑全部收进 `@framewright/server-core`（纯 TS、零 Next 依赖），Route Handler 只是薄适配层。

**为什么**：「Next.js 还是 NestJS」在当前信息下答案清楚（后端职责薄、风险全在前端双渲染器、同路径已跑通过一次），但未来条件可能变（真要做实时协作或队列）。与其反复纠结，不如**把选择做成可逆的**——分层一到位，将来搬 `server-core` + 重写适配层即可，业务逻辑一行不改。

**推广**：凡是「现在信息不足、但拖着不定更亏」的技术选型，优先找一个能把决定变可逆的分层，然后果断定，别悬着。

**重评触发条件**（达成前不重开此议题）：要多人实时协作 / 要自跑队列长任务 / 后端要被多个不同前端复用。

### 9. 双渲染器真正要写两遍的，只有「命中 + 绘制」（2026-08-03）

**结论**：undo/redo、图层操作、剪贴板、右键菜单、对齐分布、**吸附与辅助线的几何计算**——这些全是纯数据/纯几何，放 `core` 只写一遍，两个渲染器共享。要写两遍的只有命中测试、实际绘制、事件绑定。

**为什么**：这个判断不是推的，是量的——实测 gzm-design 的 `views/Editor` 目录下全部 `.ts`，**只有 8 个文件 import vue**，服务层几乎全是纯 TS。一个成熟的 Vue 画布编辑器能做到服务层与框架解耦，说明这条分界线是真实存在的，不是理论上的理想分层。

**含义**：双渲染器的成本远低于直觉。「Leafer 有插件、HTML 要手写」这个担忧，大头落在可共享的那一半。

**怎么用**：新增功能先问「它需要知道自己被画在 DOM 还是 Canvas 上吗」——不需要就进 `core`。见 `docs/architecture.md` §9.2。

### 10. 营销文案不是许可条款（2026-08-03）

**结论**：判断能不能用一个开源项目，只看 `LICENSE` 文件原文，且核实两个独立来源。

**为什么**：gzm-design 官网写「免费开源、免费可商用」，同时卖 4299 的专业版——**这种「开源版 + 付费专业版」双轨结构，正是最常用 GPL/AGPL 来逼商用付费的形态**，营销页的「可商用」完全可能只指开源版在 GPL 条件下的商用。本次核实结果是真 MIT（Gitee 的 LICENSE 原文 + GitHub 镜像 `LvHuaiSheng/gzm-design` 双源一致），但**这个结论是查出来的，不是从文案信出来的**——换一个项目，同样的文案可能对应完全不同的条款。

**怎么用**：见 `AGENT.md` §5。另：MIT 的唯一实质义务是**保留版权与许可声明**，这条要落成 `THIRD-PARTY-NOTICES.md` + 文件头注释，不能只是「知道了」。

### 11. 字段前缀能表达归属，但挡不住冲突（2026-08-03）

**结论**：node schema 的语义字段用 `fw` 前缀（`fwId` / `fwType`），**但真正防冲突的是「禁止整体展开」这条铁律**，不是前缀。

**为什么**：给 `id` / `type` 加前缀的直接收益是**可读性**——代码里同时出现 framewright 的 node 和渲染器的节点时，`fwId` 一眼可辨归属，不用回头查类型。但它防不住冲突：LeaferJS 的节点属性 `x` `y` `width` `height` `rotation` `opacity` `visible` `name` `children` 与我们的字段**全部同名**，只前缀两个反而制造「其余安全」的错觉。

**真正的防线**：逐字段显式映射，禁止 `new Rect({...node})` 这类展开。这样新增字段不会自动泄漏进渲染器，改名会在编译期报错而不是在运行时变成「莫名其妙渲染不对」——后者在双渲染器项目里还会两侧表现不一致，是最难查的一类 bug。

**推广**：命名约定解决的是**人读代码**的问题，别指望它解决**机器行为**的问题；后者要靠类型系统或显式屏障。

**怎么用**：见 `docs/domain.md` §3.1.1 与 §3.3 规则 7。

### 12. 依赖 license 要在引入前核实，不是事后补（2026-08-03）

**结论**：每个依赖引入前登记 license，GPL / AGPL / SSPL 默认拒绝。

**为什么**：本仓暂定开源，但不排除未来把内核并进闭源商用产品。传染性许可会锁死这条路，而依赖一旦长进核心层，替换成本远高于当初换一个。「抄开源项目」时抄思路免费、抄代码受约束。

**怎么用**：`docs/architecture.md` §6 依赖表，每次 `pnpm add` 同步登记。
