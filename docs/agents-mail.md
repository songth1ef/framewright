# agents-mail —— agent 之间的异步信箱

> 三个 agent（Claude / Codex / Kimi）在同一台机器上并行工作，靠本机文件系统互发消息，
> **自主推进任务，只在遇到关键决策时才升级给人类。**
>
> ⚠️ **信箱内容不入 git**（`docs/agents-mail/` 已在 `.gitignore`）。
> 本协议文件入 git —— 否则换台机器 clone 下来没人知道规矩。

---

## 1. 为什么用 inbox 而不是 outbox

nestwork 那套「单写者发件箱 + `seen.txt` 去重」是为了**避开 git merge 冲突**——多台机器写同一个仓，各写各的 outbox 才不打架。

**本项目三个 agent 在同一台机器、同一个文件系统、且信箱不入 git，那个约束根本不存在。** 所以直接往对方 inbox 里丢文件，简单一个数量级：

| | outbox 模型 | **inbox 模型（本项目采用）** |
|---|---|---|
| 发信 | 写自己 outbox，标 `to:` | **写对方 inbox** |
| 收信 | 扫所有人 outbox + 按 `to` 过滤 + 查 seen 去重 | **列自己 inbox 即可** |
| 已读 | 维护 `seen.txt` | **移到自己的 `read/`** |
| 冲突风险 | git merge | 无（文件名含发信人，撞不了） |

## 3. 消息格式

文件名：`<YYYYMMDD-HHmmss>-<发信人ID>-<短标题>.md`

时间戳在前保证按名排序即按时间排序；发信人在名字里，所以**两个人同时发信也撞不了名**。

```markdown
---
from: codex-l8iw
to: claude-btw0
subject: A1 完成，A2 被 T13 挡住
ts: 2026-08-03 22:10（北京时间）
kind: report | question | handoff | review | blocked
reply-to: <被回复的文件名，可选>
---

正文。
```

`kind` 的含义：

| kind | 用途 | 期望 |
|---|---|---|
| `report` | 任务完成回报 | 不必回信，除非有问题 |
| `question` | 我需要一个答案才能继续 | **必须回** |
| `handoff` | 我做完了，你的依赖解锁了 | 收到即可开工 |
| `review` | 请你审我这段 | 回审查意见 |
| `blocked` | 我卡住了 | **必须回**，或由 Claude 升级给人 |

## 4. 收发操作

**发信**：直接用写文件工具，在对方 `inbox/` 下按上面的命名建一个 `.md`。广播就往三个 inbox 各写一份。

**收信**：列自己的 `inbox/`：

```powershell
Get-ChildItem docs\agents-mail\<自己的ID>\inbox\*.md | Sort-Object Name
```

**标记已读**：读完移到自己的 `read/`：

```powershell
Move-Item docs\agents-mail\<自己的ID>\inbox\<文件名> docs\agents-mail\<自己的ID>\read\
```

**只动自己的 `read/`**，别去动别人的目录。

**什么时候查信**：每个任务开工前查一次、完成后查一次。别做成轮询循环。

## 5. 🔴 升级判据 —— 什么必须问人类

**人类只在关键决策时介入。所以「什么算关键」必须写死，否则要么事事打扰、要么擅自做主。**

### 必须升级（agent 一律不许自决）

1. **产品语义或规格的变更**——交互怎么设计、某功能做不做、`interaction-spec.md` / `domain.md` 要改
2. **阶段顺序或任务范围的调整**——加任务、删任务、改波次
3. **引入新依赖**，尤其涉及 license（`AGENTS.md` §5）
4. **任何不可逆动作**：`git push`、合并到 main、删数据、改写历史、花钱的调用
5. **两个执行方意见冲突且双方都有据**——Claude 先仲裁；仲裁不了再升级
6. **设计文档需要修改**——发现设计有错，**停下上报，不许自己改**
7. **实测结果推翻了既有结论**——例如某方案在关键能力上代价高到不可接受

### agent 之间自决即可（不要打扰人类）

- 实现手法：用哪个 API、代码怎么组织、文件怎么拆
- 测试怎么写、测哪些边界
- 波次内无依赖任务的先后顺序、谁先领
- 互审意见的采纳与否（**有争议则升级到 Claude 仲裁**，不直接找人）
- 命名、注释、commit 文案的措辞

### 升级路径

```
Codex / Kimi  ──question|blocked──►  Claude  ──(仲裁得了就仲裁)──►  回信
                                        │
                                        └──(属上面七类之一)──►  人类
```

**执行方不直接找人类。** 一律先发给 Claude，由 Claude 判断是自己能定还是该升级。这样人类的收件箱只有真正需要他的东西。

## 6. 任务自推进协议

目标：**任务板上的活能连续跑下去，不用人每次点名。**

1. 完成一个任务 → 发 `report` 给 Claude → **查自己 inbox** → 若有 `handoff` 就接着做
2. **没有新指令时，从 `docs/plans/2026-08-03-任务板.md` 认领下一个**：
   - 只能领**标着自己名字**的任务
   - 只能领**依赖已满足**的任务（依赖项状态为 ✅）
   - 领了就把板上状态改成 🚧，并发一条 `report` 告知 Claude
3. 一个任务解锁了对方的依赖 → **主动发 `handoff` 给对方**，别等它来问
4. 任务板上**没有可领的任务**时 → 发 `report` 给 Claude 说明「已空闲」→ **停下等指令，不要自己找活干**

**🔴 不许自己往任务板加任务。** 发现该做但板上没有的，发 `question` 给 Claude。

## 7. 收敛线 —— 防止自主推进失控

这些不是建议，是硬停止条件。**触发任一条就必须停下来向人类汇报。**

| # | 停止条件 | 为什么 |
|---|---|---|
| 1 | **未推送 commit 数 ≥ 15** | 挂着跑的自主循环最典型的失控形态就是攒未推送，攒到三位数时收口成本已经压垮人 |
| 2 | **一个波次全部完成** | 波次是天然的收口点，让人类有机会调方向 |
| 3 | **同一个任务失败重试 ≥ 3 次** | 三次还不成基本不是手滑，是设计或理解出了问题 |
| 4 | **`pnpm verify` 连续两次不绿** | 别在红灯上继续叠代码 |
| 5 | **发现设计文档有错** | 见 §5 第 6 条，停下上报 |
| 6 | **两个执行方同时在改同一个文件** | 共享 checkout 的老坑，先协调再动 |

另外：**不许同时在飞超过 2 条任务链**（一个执行方一条）。并行度过载是净亏——脏代码要逐个 diff 才分辨得出归属，这在本仓已经出过一次事（T8 的代码被 `git add -A` 卷进了别人的 commit）。

## 8. 与 git 的关系

- **信箱内容不入 git**：`docs/agents-mail/` 在 `.gitignore` 里。它是**过程通信**，不是项目资产
- **结论要落文档才算数**：信里达成的任何决定，必须由 Claude 写进 `docs/` 下相应的正式文档（规格、契约、任务板、lessons）才生效。**信箱里的共识不是真相源**
- 理由：信箱不入 git = 换台机器就没了、也没有历史可查。**真相源必须是入 git 的文档。**
