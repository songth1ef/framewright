## 验收铁律（所有任务通用）

1. **`npx tsc --build` 必须 0 error** —— 只跑 vitest 不算数。
   历史教训：出过「72 条测试全绿，而 tsc 报 9 个 possibly undefined」。
2. **绿色不构成证据**。性能数字必须附「确实在干活」的旁证
   （画面指纹变化、内存差异、真实解码帧数），否则一律不采信。
   历史教训：Leafer 视频探针曾给出 60/59.7/58.9 fps 的漂亮数字，
   但画面指纹全程不变、1/4/8 路内存完全相同 —— 数字是假的。
3. **单次采样不算数**。已实测出系统性偏差：16 个单次采样值**全部低于中位数**。
   性能结论必须多次采样取中位数。
4. **状态不许存在渲染器内部**，会话状态归 host。
5. **提交用 `git commit -- <具体路径>`**，新文件先 `git add <文件>`。
   禁止 `git add .` / 裸 `git commit` —— 有并行 agent，裸提交会扫走别人的改动。
   历史教训：确实发生过，9 个别人的文件被扫进一个标着 `docs(architecture)` 的提交。
6. **仓库要脱敏与用户公司相关的一切数据**，只用公开素材。

## #16 裁剪保留区改矩形 + 上限可配

**用户原话要点**：缩放到超大视图时，中间保留的是**一个圆形**，「有点像我的世界」；
最好是矩形；那个 1500 的数量用户也应该可以自己配，根据机器性能调高调低。

### 根因（已定位）
`packages/core/src/viewport-culling.ts:79-83`，`squaredDistanceToRectCenter` 返回
`deltaX² + deltaY²` —— 各向同性，等值面就是圆。
视口是矩形（约 16:9），用圆盘去填矩形预算，要覆盖四角就必然在上下方向浪费大量预算。

### 修法
排序度量改成按视口半宽/半高归一化：`max(|dx|/halfW, |dy|/halfH)`。
等值面变成与视口同宽高比的矩形，同样预算覆盖更多真正可见区域。

⚠️ `getConnectionsInViewport`（同文件第 386 行）有同样的欧氏排序，
但那是 #17 的领地，本任务**不动**，避免并行冲突。

### 另一半
`maxNodes` / `maxConnections` 开放为用户可配（UI 入口 + 持久化 + 范围校验），
参考既有 `interaction-mode-storage.ts` / `minimap-storage.ts` 的模式。

## #17 fan 模式：1 万条线汇聚单点仍卡死

**用户原话要点**：1 万节点其他模式已经丝滑，但 fan 模式（1 万条线全连到同一个节点）
还是超级卡顿。

### 根因（已定位，尚未修）
`viewport-culling.ts:366-390`：**`maxConnections` 只截输出，不截工作量**。
每次重算都把全文档 1 万条连线**全部**物化成候选对象、算中点、排序，
最后才在第 410 行丢掉 9000 条。

雪上加霜：fan 模式所有线共享同一端点，它们的 bezier AABB 几乎都包含目标节点，
**裁剪几乎裁不掉任何一条**，于是永远顶着 1000 条上限跑。
而已实测：同样 1499 节点，有无 1000 条连线的差异是 **22.54 vs 44.09 fps** ——
连线是当前最大的性能杠杆。

### 候选方向（需实测排序，不要凭直觉全上）
1. 让上限真正截住**工作量**，而不只是输出（早退、分桶、或按端点聚合预筛）
2. 低 LOD 下 bezier 降级为直线，省掉三次曲线求解
3. **把 N 条线合并进单个 path 元素**（DOM 用一个 `<path>` 多段子路径，Leafer 用单 Path）
   —— 元素数量很可能才是主因
4. 大量线汇聚同一节点时，考虑「聚合/收束」表达

必须给出改前改后的 fps 与最大帧耗时对比。

## #19 小地图：可辨形状 + 类型标识 + 内容缩略

**用户原话要点**（连续两轮反馈同一处）：

- 左下角小地图现在看不到节点缩略图，只能看到位置。
  比如画布上是九宫格 9 张图，小地图里也应看得出是这 9 张图，而不是 9 个无差别方块。
- **全是点**，「太模糊了」「很奇怪」「不知道具体的位置」。
  要「加上一些方块嘛，或者一些矩形、四边形」，
  并且「一眼能看出他的视频啊，或者是图片这种标识会更清晰一点」。

### 分三层做，按性价比从低到高

1. **形状**（先做，最便宜）：节点画成矩形，按真实宽高比铺，而不是无尺寸的点。位置与占位一眼可辨。
2. **类型标识**：图片 / 视频 / 音频各自的小 SVG 图标或明确视觉区分。
3. **内容缩略**：图片节点在小地图里能看出缩略内容。

📎 关联：画布自身的 `dot` LOD 档位（scale < 0.2）同样把节点降级成点，
「一眼看出类型」的诉求在那里同样成立。可一并评估，但不要因此拖慢小地图这条主线。

### 待澄清
「增加内容」的具体所指未定，候选：当前视口框、节点类型区分、点击/拖拽跳转。
**先实现缩略图这一确定项**，其余列为待确认。

### 🔴 性能约束
小地图是全局视图，10000 节点时不能为了缩略把性能拖垮。
缩略必须走低成本路径（复用已解码资源 / 离屏合成 / 降采样），
**不能给每个节点再挂一份真实媒体元素**。
必须实测 10000 节点下开启缩略前后的帧率差异。

### 已知环境问题
后台派发经常被批量中止（已发生 8+ 轮）。应对方式已固化为
**「一次一小步、做完就提交」** —— 中止从「全盘丢失」降级为「丢一小步」。
每轮开始先收残留（`git status` 有改动就跑测试、绿则提交）。

**本轮新增教训**：用 `cmd &` 在 Bash 工具里放后台会**秒退** ——
外层调用一返回，子进程即被回收；codex 还会卡在 `Reading additional input from stdin...`。
正确做法：让 Bash 工具自己托管前台进程（`run_in_background`），并 `< /dev/null` 关掉 stdin。
