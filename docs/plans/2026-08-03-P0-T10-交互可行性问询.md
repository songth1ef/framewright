## 为什么现在做

交互是 `RendererAdapter` 里**最容易被单一实现带偏**的部分：DOM 有事件冒泡与 CSS 命中测试，LeaferJS 有自己的事件系统与命中检测，两者差异远大于「画一个矩形」。

而现在是定它最便宜的时刻——**两个渲染器都已完成，两边的实现者都能立刻回答「这个回调我这边给得出来吗」**。等 P2 开工才定，等于把最难的接口决策推到最贵的时候做。

**独立填写、互不可见**的理由同 T6：如果参照对方的答案，只对一侧自然的设计会被顺着抄过去，缺陷就留在契约里没人发现。

## 回调契约草案（待你评估，不是定稿）

```ts
export type SelectionMode = 'replace' | 'toggle' | 'add'

export interface RendererCallbacks {
  onSelectionChange(fwIds: readonly string[], mode: SelectionMode): void
  onNodesMove(moves: ReadonlyArray<{ fwId: string; x: number; y: number }>): void
  onViewportChange(viewport: Viewport): void
  onNodeActivate(fwId: string): void
}
```

设计前提（供你判断草案是否成立）：

1. **回调是语义的，不是事件的**——不允许上抛 `MouseEvent` / `WheelEvent` 之类。上层不该知道用户用的是中键还是空格。
2. **`onNodesMove` 在拖拽结束时触发一次，不逐帧**——逐帧会让一次拖拽产生几百条撤销日志。拖拽过程中的预览由渲染器自己画，属纯呈现，不进状态。
3. **选中粒度恒为业务单元**，永不选中业务单元的内部元素（内部元素本就不在 node 树里，见 `docs/domain.md` §2.2）。
4. **坐标换算、锚点缩放、框选相交判定拟全部放进 `core`**（纯数学/纯几何，两侧共享），渲染器只负责「感知手势」与「画出反馈」。见 `docs/architecture.md` §11.2。

## 问卷正文

对 **A–F 每一项**，逐条回答下面 5 问。**不要合并作答，一项一节。**

> ### 交互 X（照抄标题，如「交互 A 平移画布」）
>
> **Q1 监听方式**：你这一侧用什么 API 监听到它？写出**具体的调用/事件名**，不要写「监听鼠标事件」这种概括。
>
> **Q2 原始数据**：触发时你能直接拿到什么？屏幕坐标、画布坐标、还是已经算好的 delta？坐标原点在哪？是否已含缩放？
>
> **Q3 缺什么**：要产出草案里的语义参数，你还缺什么？**具体写出你希望 `core` 提供的函数签名**（例：`screenToCanvas(viewport, point): Point`）。
>
> **Q4 坑与做不到**：这一项在你这一侧有什么已知的坑、限制、或做不到的地方？**这一栏最有价值，不要写「无」敷衍。**
>
> **Q5 中间态反馈**：拖拽预览 / 选框 / hover 高亮这类未提交的中间态，你打算怎么画？**会不会需要往 `RenderContext` 加字段？** 如果需要，写出你想加什么。

### 最后三问（全局）

**Q6 契约缺陷**：看完上面的 `RendererCallbacks` 草案，**有哪个回调你这一侧给不出来、或者签名不对**？具体说明并给出你认为对的签名。

**Q7 多出来的需求**：草案里**没有**、但你认为必须有的回调是什么？为什么。

**Q8 事件冲突**：A–F 六项在你这一侧会互相打架吗？（例：中键拖拽与浏览器自动滚动、滚轮缩放与页面滚动、框选起点落在节点上还是空白处的判定）写出你预见的冲突与你打算怎么解。

## 增量补答（**仅 DOM 侧需要**，Leafer 侧直接按上面完整作答）

DOM 侧已在 `docs/plans/answers/T10-dom.md` 完成首轮作答，**但那一轮是在 `docs/interaction-spec.md` 写出来之前做的**，规格里下面这些当时不在问卷范围内。请**追加**到原答案文件末尾，不要重写已答部分。

对下列每一项，仍按 **Q1 监听方式 / Q2 原始数据 / Q3 缺什么 / Q4 坑与做不到 / Q5 中间态反馈** 五问作答：

### 补 A′：平移的另外三种触发

规格里平移有四种触发，首轮只答了中键。补答：

- **空格按住 + 左键拖拽**（需要全局键盘状态，且空格可能被页面滚动/按钮激活抢走）
- **触控板双指滑动**（在 wheel 事件里表现为 `deltaX/deltaY` 且通常 `deltaMode === 0`，如何与滚轮缩放区分）
- **`Shift` + 滚轮 = 水平平移**（与 B 的滚轮缩放共用 `wheel` 事件，如何分派）

### 补 B′：缩放的快捷键与两个视图命令

- `Ctrl` + `=` / `Ctrl` + `-`：**以视口中心为锚点**步进一档
- `Shift` + `1` 适应内容：缩放到刚好容纳全部节点、四周留 5% 边距——**你这一侧算得出「全部节点的包围盒」吗，还是需要 `core` 提供？**
- `Ctrl` + `0` 实际大小：回 100% 并居中于内容

### 补 G：等比缩放（新增交互项）

- 选中框的**四角**控制点拖拽等比改变尺寸
- **只有四角，没有边中点**——生成结果不允许被自由拉伸变形（产品决定，不是技术限制）
- 控制点的命中区域通常要比视觉尺寸大（否则难点中），你这一侧怎么做

### 补 H：键盘操作

- `Ctrl` + `A` 全选、`Esc` 清空、`Delete` / `Backspace` 删除选中
- 方向键移动 1px、`Shift` + 方向键移动 10px
- **键盘事件绑在哪？** 画布容器需要 `tabIndex` 才能接收吗？焦点跑到别处时怎么办？与页面上其它输入框的冲突怎么避免？

### 补 I：不随缩放变化的视觉元素

规格要求**选中描边恒为 2px 视觉宽度、控制点恒为固定视觉尺寸**，即缩放到 400% 时它们不能跟着变粗变大。

- 你这一侧怎么实现 `1 / viewport.scale` 反向补偿？
- 有没有更省事的做法（例如把选中层放在不受 transform 影响的 overlay 里）？
- 这个补偿会不会引入 0.5px 之类的渲染瑕疵？

### 补 J：光标反馈

规格给了六种光标状态（`default` / `grab` / `grabbing` / `move` / `nwse-resize` / `crosshair`）。你这一侧切换光标的机制是什么？手势中途被 `pointercancel` 打断时怎么保证光标复位？
