## 0. 阶段重排（2026-08-03，Claude 的判断）

原顺序 `P1 持久化 → P2 交互` 是按工程直觉排的（骨架先于交互），**不是按「对选型结论的贡献」排的**。按贡献重排：

| 对选型结论的贡献 | 事项 | 原阶段 | 新阶段 |
|---|---|---|---|
| 🔴 可能**直接决定**结论 | 视频节点内嵌播放器（开环 #9） | P1 | **P1a** |
| 🔴 「使用体验」维度**完全依赖**它 | 交互（拖拽/缩放帧率、跟手感） | P2 | **P1b** |
| 🟡 「多节点渲染性能」的真实负载 | `ai-image`/`ai-video` 真实渲染 | P1 | **P1a** |
| ⚪ **零贡献** | 持久化 / 后端 / 撤销 | P1 | **P1c** |

**持久化对「DOM 还是 LeaferJS」贡献为零**——后端与渲染器选型完全无关。它服务的是 MVP 判据里的「作品可展示」，不是「选型结论」，却排在最前面。

**重排后的收益**：选型结论在 **P1a + P1b 结束时就出来了**。若 Leafer 在视频播放器或交互上代价高到不可接受，可当场止损，不必把持久化那一整块也做两遍。

| 阶段 | 内容 | 产出 |
|---|---|---|
| **P1a 渲染能力** | core 纯函数、schema 扩展、生成单元四态、连线、**视频播放器实测** | 多节点渲染性能与媒体能力的对照数据 |
| **P1b 交互** | 无限画布全套，契约已定案 | 使用体验维度的对照数据 → **选型结论可出** |
| **P1c 持久化** | 后端、`documentId`、撤销日志、provider mock | 端到端跑通、作品可展示 |

**A1 要点**：`zoomAtPoint` 的硬性语义是「光标下的画布点缩放前后不动」，这是最容易实现错的地方（错了表现为画布往光标反方向滑走）。`normalizeWheelSteps` 见契约 §5 的说明——鼠标大 delta 与触控板连续 delta 的归一化常数必须统一。

**A2 要点**：框选是**相交**不是完全包含；排除 `locked` 与 root；`rotation` 首版按 AABB（契约裁决 9）。

**A4 要点**：`computeMoves` 必须处理「父子同选时只保留最上层」（防后代被移动两次），且输出是**父相对坐标 + `parentFwId`**（契约 §2）。

**B1 要点**：见 `docs/domain.md` §3.2.1 与 §3.2.2。`sourceFwIds` 只在生成单元上。demo 文档要加**至少一组溯源关系**（一个 `ai-image` → 两个 `ai-video`），供后续连线渲染与测试使用。

## 2. 通用纪律（每个任务都适用）

摘自 `AGENTS.md` 与 `docs/plans/2026-08-03-P0-编排与分工.md`，**不再逐份提示词重复**：

1. **先写失败测试 → 跑一遍确认它真的失败 → 再实现**，确认失败那步不许跳过
2. **只做分配给你的任务号**，不许顺手做下一个，不许「看到问题顺手改」别的文件
3. **不许改设计文档**。发现设计有错、有矛盾、写不出来 → **停下上报**
4. **不许 `git push`**，只 commit；**不许 `--no-verify`**；**不许 `--update-snapshots` 抹平基线变化**
5. **每个任务结束跑 `pnpm verify`**，全绿才算完成
6. **禁止把 node 对象整体展开进渲染器**（`{...node}`），必须逐字段显式映射
7. **任何切换后必须保留的状态不许存在渲染器内部**
8. **上层不许出现渲染器品牌分支**（`if (adapter.id === 'leafer')`）
9. **两版同步**：一个功能两侧都能用才算完成；一侧确实做不到，注册显式的 unsupported 实现 + 在成本报告写清技术原因
10. 回报用统一格式，**「接口摩擦」栏不许留空敷衍**
11. **🔴 不许改本任务板和 `docs/progress.md` 的状态**——它俩由 Claude 独占维护。你只管在回报里写清任务号与 commit sha，状态我来标。

### 为什么第 11 条要单列

两个执行方在同一个 checkout 上并行，**真实碰撞面只有这两个文件的状态列**——代码层面 `renderer-dom` 与 `renderer-leafer` 按包预先切开，天然不重叠。

考虑过给每个执行方开独立 git worktree（业界主流做法，Vibe Kanban 等都这么干），**但对本项目是净负担**：

1. **信箱在 `.gitignore` 里，而 ignored 文件在 worktree 之间不共享**——每个 worktree 各有一份 `docs/agents-mail/`，两边互相看不见对方的信，协作通道直接断掉
2. 两个渲染器都依赖 `@framewright/core`，分 worktree 后一边改了 core 另一边看不到（波次 3 的 D0 正是要改 core）
3. 每轮合并的负担全压到编排方

业界用 worktree 是因为他们的 agent 做的是**互相重叠的 feature**；我们是**按包预先切开的**，用不上那个隔离，却要吃它全部的代价。

**把状态列收归单一写者，就消掉了那两个文件的碰撞**，成本为零。

## 3. 冲突规避（共享 checkout，两个 agent 同时在飞）

**这条已经出过事**：T8 的代码被 `git add -A` 卷进了别人的 docs commit。

- **`git add` 前必须先 `git diff --stat`**，行数不对就说明有人插了活，只 add 自己的文件
- **不许用 `git add -A`**，按路径 add
- **不许 `reset` / `rebase` 别人的 commit**；发现自己的 commit 上压了别人的提交就放弃改写历史
- 波次内的任务已按**文件不重叠**划分：`renderer-dom` 与 `renderer-leafer` 天然隔离；core 的四个文件互不相干
