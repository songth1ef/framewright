# architecture — 架构与选型

> 模块边界、数据流、选型理由、依赖表、开环清单。
> 阻塞 P0 的开环已全部闭合（2026-08-03）。当前状态见 `docs/progress.md`。

---

## 1. 核心命题

> **一份 JSON node 树，两套渲染器，渲染出同一个画布，并且能在运行时一键切换。**

这是本项目存在的理由。所有架构决定都服务于一个可回答的问题：
**做 AI 画布工作台，画布层用 DOM（Next.js/tsx 组件）还是 LeaferJS？**

因为作者事先不知道哪个更好，所以答案不能靠纸面推演，只能靠**并行实现 + 现场对比**。于是「渲染层可插拔、可在线切换」从一个「架构优点」升格成**项目的第一需求**。

架构的第一原则由此确定：**让两个渲染器可以被公平对照，且能在同一份数据上原地互换。** 任何让某一侧「偷跑」的设计（把选中态塞进 Leafer 节点、把视口存在 DOM 容器上）都会同时污染结论、并在切换时当场丢状态。**切换是最好的架构测试仪。**

## 2. 分层

```
            ┌─────────────────────────────────────┐
            │            apps/web (UI)            │  工具栏 / 图层面板 / 属性面板 / 生成入口
            │  ┌───────────────────────────────┐  │  ┌──────────────────┐
            │  │        RendererHost           │◀─┼──│ 渲染器切换开关   │
            │  │  持 container，装/卸 adapter   │  │  └──────────────────┘
            │  └───────────────┬───────────────┘  │
            └──────────────────┼──────────────────┘
                               │  RenderContext（树 + 选中 + 视口 + 回调）
            ┌──────────────────▼──────────────────┐
            │        @framewright/core            │  node schema · 树操作 · 会话状态 · RendererAdapter
            └───────┬─────────────────────┬───────┘
                    │                     │
    ┌───────────────▼──┐              ┌───▼─────────────────┐
    │ renderer-dom     │              │ renderer-leafer     │   ← 两个实现，同一个接口
    │ (React/tsx)      │              │ (LeaferJS)          │      运行时可互换
    └──────────────────┘              └─────────────────────┘

服务端（同一个 Next.js 应用内）：

            ┌─────────────────────────────────────┐
            │   apps/web/app/api/**  Route Handler │  薄适配层：解析请求 / 鉴权 / 调 server-core
            └──────────────────┬──────────────────┘
                               │
            ┌──────────────────▼──────────────────┐
            │    @framewright/server-core         │  纯 TS，零 Next 依赖
            │  Document 存取 · 生成任务编排 · 素材  │  ← 全部业务逻辑在这里
            └──────────────────┬──────────────────┘
                               │
            ┌──────────────────▼──────────────────┐
            │      @framewright/provider          │  AI 生成能力接口 + mock 实现
            └─────────────────────────────────────┘
```

**边界规则**

- `core` **零渲染依赖**——不 import React，不 import leafer。它是纯 TS。
- 两个 renderer 实现同一个 `RendererAdapter` 接口，互不感知对方存在。
- `apps/web` 只依赖 `core` 与 `RendererAdapter`，**不允许出现渲染器品牌分支判断**；切换渲染器靠注入不同实现。
- `provider` 只定义「怎么发起生成、怎么拿结果」，不含任何具体厂商实现。

## 3. 数据流

```
用户操作（拖动/改属性/新建）
   → 应用层派发一个对 node 树的变更
   → core 更新 node 树（唯一真相源）
   → 通知当前 renderer 重绘受影响子树
   → renderer 把交互事件（点击/拖拽结束）抛回应用层
```

```
用户发起生成
   → provider.submit(params) → 得到 generationId
   → 轮询 / 订阅 status
   → succeeded 时把结果 URL 写成新的 img/video node 挂进树
```

**关键约束**：渲染器**永远不直接修改 node 树**。它只上报「用户想做什么」，改树是应用层的事。这条一破，两个渲染器就会各自长出一套隐式状态，对照实验作废。

## 3.5 运行时切换机制

`RendererHost` 是 `apps/web` 里唯一持有画布 DOM 容器的组件。切换流程：

```
用户点切换开关
  → host 调 当前adapter.destroy()          清空容器、解绑监听、释放实例
  → host 调 新adapter.mount(container, ctx) 用同一份 RenderContext 重新挂载
  → 画面、选中、视口 三者与切换前一致
```

**为什么这样切是安全的**：`RenderContext` 里已经包含了重建画面所需的全部信息（node 树 + 选中集 + 视口）。渲染器是无状态的投影，销毁重建不丢东西。

**两个渲染器都是运行时依赖**（不是构建期二选一），因为要在同一个页面里互换。若包体积成为问题，用动态 import 懒加载未激活的那一个——但**不能**做成构建期开关，那样就切不了。

**已知的最难统一处 = 交互事件。** DOM 有原生事件冒泡与 CSS 命中测试；LeaferJS 有自己的事件系统与命中检测。拖拽、框选、缩放平移这三件事在两侧的实现差异会很大。`RendererAdapter` 的回调契约必须定义在**语义层**（「用户把节点 X 拖到了 (x,y)」「用户框选了区域 R」「用户把视口缩放到 s」），而不是事件层（不要往上抛 `MouseEvent`）。**这一处是整个选型验证里信息量最大的地方，也最可能推翻直觉。**

## 4. 已定选型

| 项 | 决定 | 理由 |
|---|---|---|
| 包管理 | pnpm workspace monorepo | 双渲染器天然需要多包；用户既有栈就是 pnpm |
| 语言 | TypeScript strict | node schema 是本项目的核心资产，必须类型化 |
| 画布方案 | DOM 与 LeaferJS **并行两套** | 这就是要验证的东西本身 |
| 渲染层 | **可插拔 + 运行时一键切换**，非构建期二选一 | 作者事先不知道哪个更好；切换是最好的对照装置与架构测试仪 |
| DOM 侧形态 | React / tsx 组件 | 用户明确要求「html 组件版本 nextjs(.tsx)」 |
| 功能推进 | 两版**同步开发**，不许单侧先行 | 单侧先行 = 对照实验作废，且回头补等于不补 |
| 交互事件契约 | 定义在**语义层**，不上抛原生事件对象 | 两套事件系统无法在事件层统一 |
| MVP 成功判据 | **端到端跑通 + 作品可展示**；选型结论是副产品 | 用户 2026-08-03 确认 |
| 后端 | **完整后端一次到位**，形态 = **Next.js 全栈**（Route Handlers + Prisma），不用 NestJS | 见 §4.1。风险（三条战线）用 §5.1 阶段排序化解 |
| 后端分层 | 业务逻辑全在 `@framewright/server-core`（纯 TS、零 Next 依赖），Route Handler 只当薄适配 | **让选择可逆**：将来要拆独立 NestJS，搬 `server-core` + 重写适配层，业务逻辑一行不改 |
| app 壳子 | **Next.js**（随后端决定自动关闭） | 后端选 Next.js 全栈后，若前端用 Vite 就还是两个应用，那不如直接上 NestJS |
| 布局 | 绝对定位 x/y/w/h | 先跑通；布局引擎见开环 #6 |
| z 序 | 兄弟数组顺序 | 避免 zIndex 与数组顺序两份真相 |
| 元素集 | 只做 frame / box / img / video | 四个足够暴露两个渲染器的差异，多做是浪费 |

### 4.1 为什么后端是 Next.js 而不是 NestJS

1. **后端职责很薄**——CRUD 一棵 JSON 树、代理生成请求、轮询状态、素材落地。没有队列、没有自跑长任务、没有实时协作（第一版明确不做）。NestJS 的 DI / 模块化在这个体量上是空转。
2. **项目的全部风险在前端双渲染器**。前端已因「双实现 + 功能同步 + 插件对齐」翻倍，后端再开一条独立战线是在低价值处烧预算。
3. **同一条路作者已跑通过一次**——`mingtu`（Next.js 15 + `leafer-ui`/`leafer-editor` + `better-sqlite3` 直连 + 自建鉴权 + 对象存储 + standalone/PM2 自部署）证明单个 Next.js 应用能扛下画布 + 数据 + 部署全套。
4. **与「独立可挂载」最兼容**——Next.js 走 Multi-Zone 官方路径；单应用单次部署即有在线 demo。

**什么时候该改选 NestJS**（触发条件，达成时重评）：要做多人实时协作 / 要自跑队列与长任务 / 后端要被多个不同前端复用。三条都不成立时不重开此议题。

## 5.1 阶段排序（防三条战线并行）

「双渲染器 + 完整后端 + 真实生成」三件事一起开工是明确的失败模式。用**排序**而不是自觉来防：

| 阶段 | 目标 | 范围 |
|---|---|---|
| **P0 接口夹逼** | 逼出正确的 `RendererAdapter` 形状 | **两个渲染器同时写，但功能面极小**：只渲染 frame + box，静态，无交互。后端不动。 |
| **P1 骨架贯通** | 端到端一条线跑通 | Next.js Route Handlers + `server-core` + Prisma 存取 Document；画布改动能存能读，刷新还在。生成先用 mock provider（提交→轮询→返回占位素材）。 |
| **P2 交互补齐** | 画布真能用 | 拖拽、框选、缩放平移、属性编辑。**两版严格同步**。切换开关此时上线并纳入冒烟。 |
| **P3 真实生成** | 作品完整 | 接真实 provider，img/video 节点接真实素材。 |

**P0 为什么必须两版同时写**：只用一个实现去定接口，定出来的接口必然是偏那一侧的（先写 DOM 就会漏掉 Leafer 的命中检测与坐标系差异，反之亦然）。**接口的正确形状只能靠两个实现从两边夹出来。** 这也正好落实「两版同步开发」，而不是嘴上说说。

P0 功能面小是刻意的——两遍的成本此时最低，返工也最便宜。

## 7. 测试策略（规划）

- `core` — 纯逻辑，单元测试覆盖 node 树操作（增删改、层级移动、z 序、坐标累加）。这是最该测的一层。
- `renderer-*` — **对照测试**：同一份 node 树喂给两个渲染器，断言产出的几何结果一致（位置、尺寸、层级）。这层测试的价值是「防止两个实现悄悄分叉」。
- **切换测试**（本项目特有，优先级高）：构造一份带选中与非默认视口的状态 → 切换渲染器 → 断言 node 树、选中集、视口三者不变，且旧渲染器的 DOM 与监听器已清空。这条测试直接守着 `AGENTS.md` 的「状态不许渗进渲染器」禁止项。
- `apps/web` — 端到端只覆盖主路径（新建节点 / 拖动 / 发起生成 / 结果落回画布）。
## 8. 选型结论怎么产出（本项目的真正交付物）

结论不是一句「Leafer 更好」，而是**两张表**。它们比任何主观印象都硬，且从 P0 就开始积累。

### 8.1 运行表现对照表（可复跑的 benchmark）

指标取自作者关心的三件事：**加载速度、多节点渲染性能、使用体验**。

| 维度 | 指标 | 测法 |
|---|---|---|
| 加载速度 | 渲染器 bundle 体积、首次可交互耗时 | 构建产物大小 + `performance` 打点 |
| 多节点渲染 | N = 100 / 500 / 2000 节点的首次渲染耗时、内存占用 | 同一份 node 树喂两侧，脚本化跑 |
| 使用体验 | 拖拽帧率、缩放平移帧率、点击到高亮的延迟 | 脚本驱动固定操作序列，采样帧间隔 |

**数字必须可复跑**，不接受一次性手测印象。benchmark harness 独立于单测。

### 8.2 实现成本对照表（**比性能数字更能决定选谁**）

LeaferJS 有现成生态（`leafer-editor` 等提供选中框、变换、辅助线/吸附），DOM 侧多半要手写。**这个不对称不是「要抹平的差异」，它就是结论本身。**

因此每实现一个功能，两侧各记一行：

| 功能 | Leafer 侧做法 / 耗时 | DOM 侧做法 / 耗时 | 备注 |
|---|---|---|---|
| _(示例)_ 吸附辅助线 | 装 `leafer-editor`，接 API，2h | 手写命中计算 + 参考线绘制，2d | 差 8 倍 |

#### 🔴 已预见的最大差异项：画布内可播放的视频节点

对标产品实图显示，视频节点**内嵌真实播放器**（播放/暂停、进度条、时间、音量、截图），且能在画布上直接播放。两侧代价差距极大：

> ⚠️ **本节 2026-08-04 大幅订正**。原判断「Canvas 无 `<video>`，只能逐帧取纹理或叠 DOM」**过于悲观，已被实测推翻**。

**实测（读 `node_modules` 里 `leafer-ui@2.2.9` 的类型定义，即我们实际依赖的版本）**：LeaferJS **有一等公民的视频抽象**——

```ts
interface IVideoDecoder {
  width; height; duration; currentTime; volume
  readonly paused; readonly ended; loop
  load(): Promise<void>;  play(): void;  pause(): void
  render(canvas, x, y, width, height, leaf, paint, imageScaleX, imageScaleY): void
  destroyDecoder(): void;  close(): void
}
type IVideoFileType = 'mp4' | 'webm' | 'ogv'
interface IVideoPlayOptions { autoplay?; muted?; loop?; paused? }
```

外加 `LeaferVideo extends LeaferImage`、`ImageManager.loadVideo()`、`IMultimediaType = 'image' | 'film' | 'video'`（`film` 是另一套逐帧序列的解码器）。

**修正后的判断**：

| | `renderer-dom` | `renderer-leafer` |
|---|---|---|
| 播放能力（播放/暂停/seek/音量/循环） | `<video>` 原生 | ✅ **`IVideoDecoder` 一等公民支持**，不是自己搭 |
| **播放控件 UI**（进度条、按钮、时间、音量滑块） | HTML 元素直接可用 | ⚠️ **仍要自绘 + 自做命中测试** |
| 多视频同时播放 | 浏览器管理 | 🟡 **未实测**——Leafer 的解码路径在多路并发下的性能与内存表现未知 |

**所以差异从「能力有无」缩小到「控件 UI 与并发表现」**——仍然值得测，但**不再是我原先判断的「决定性差异」**。

⚠️ **本条修正的来源值得记**：是用户凭印象提出「Leafer 应该支持视频」，我去查了实际安装版本的类型定义才发现原判断错了。**我此前那句「Canvas 里没有 `<video>`」是从通用常识推的，没有查过 LeaferJS 本身。**

⚠️ **必须提前到 P1 验证，不要拖到 P3。** 理由：如果 Leafer 在这一项上代价高到不可接受，那结论在 P1 就已经出来了，后面两个阶段的双版本投入可以及时止损；反过来，等 P3 才发现等于白做两个阶段。

（若 `renderer-leafer` 的解法是「在 canvas 上叠 DOM」，要如实记为一次**能力让步**——那意味着它在这一项上没有真的用 Canvas 方案解决问题，这个事实本身就是结论的一部分。）

#### 🔴 DOM 侧实测结果（2026-08-05，`codex-dom-video`）

**表面数据看起来是碾压性的：**

| 项 | 实测 |
|---|---|
| 生产组件代码 | **28 行** |
| 自绘控件代码 | **0 行**——一个 `controls` 属性同时给到播放/暂停、进度条、时间显示、音量 |
| 核心实现耗时 | 约 47 秒（可由测试时间戳复核） |

四项能力**不是四段独立实现**，所以无法诚实拆成四个开发时长——这一点执行方主动说明了。

**但「白送」有一笔没写在价签上的代价。**

原生控件的 UA shadow tree 是封闭的，浏览器**不告诉你用户点的是画面还是控制条**。
后果是拖进度条超过 4px 会把整个节点一起拖走。我们靠「画布优先 + 激活态」裁定绕开
（见 `interaction-spec.md` 附录 A），实现后确认的额外代价有四条：

| # | 隐藏代价 | 性质 |
|---|---|---|
| 1 | **命中切换粒度只能是整个宿主**——未激活时必须把整个 `<video>` 设 `pointer-events: none`，无法只关闭控件区域 | 能力受限 |
| 2 | **进入激活的那次点击会被消费**——事件目标在 `pointerdown` 前已确定，用户实际要点第三次才能操作控件 | ⚠️ **真实体验代价** |
| 3 | **激活后画布 hover 反馈要让路**——否则视觉上同时暗示「控件接管」和「节点可拖」 | 状态机复杂度 |
| 4 | **需要 renderer 本地生命周期治理**——激活态不属于 node schema，但要在 update/destroy 时防悬空 | 额外胶水 |

**结论：DOM 的视频节点不是「零成本」，是「零绘制成本 + 一笔交互控制权的代价」。**

Leafer 侧自绘控件要写更多代码，**但命中测试完全在自己手里，第 1、2、3 条都不存在**。
所以成本表不能只比「28 行 vs 自绘多少行」——**要把「宿主级命中切换、显式激活态、
进入点击被消费、hover 与生命周期治理」一并计入 DOM 侧。**

##### 但两侧「变慢的形态」完全不同，这比绝对值更要紧

- **DOM：60 → 31 → 30。** 一步阶跃后**稳住**。`60 → 30` 恰好是 vsync 减半的典型特征 ——
  主线程守不住 16.7ms 预算时，合成器锁到 33.3ms 并保持。
- **Leafer：60 → 45 → 11。** 连续劣化，最后**崩掉**，且 3 秒窗口里出现 33 个长帧。

##### 🔴 决定性的一条：视频播放与应用渲染循环是否解耦

`<video>` 由浏览器合成器独立播放，**不经过我们的渲染循环**。

Canvas 方案没有这个解耦：**视频每一帧都要在 rAF 里被 `drawImage` 进画布** ——
rAF 慢下来，视频就是真的卡。所以 Leafer 那个 11fps 不只是「页面动画掉帧」，
**是用户看到的视频本身在卡**。

**这是架构性差异，不是调优能抹平的。**

1. **内存两侧都没有数据。** 不是遗漏，是页面级 API 测不到视频解码缓冲与 GPU 显存。

2. **「长帧 0」有一半是阈值定义的结果。** 阈值是 50ms，而稳定 30fps 的帧间隔是 33.3ms，

   而不是「完全不卡」。Leafer 的 33 个长帧则是实打实的尖峰。
3. **严格可比性只有执行方的声明作保证。** DOM 侧的 JSON 记录了完整负载口径
   （节点 460×260、视口 1024×700、全部 muted、长帧阈值 50ms、浏览器版本），
   **而 Leafer 那份 JSON 没有 `workload` 块**。执行方声明两者口径一致，但产物层面无法核对。
   → **已排任务：Leafer 探针补记 `workload` 块并重跑一次。**

|---|---|---|
| **Leafer** | = rAF fps（4 路 60、8 路 **20**） | 同左，两者是同一个数 |
| **DOM** | **始终实时**（已由 progressDelta 证明） | 4 路 31、8 路 30 |

##### 发现一：Leafer 的视频**没有掉队**，掉的是「画出来的那一半」

之前我说「Leafer 的 rAF 就是视频渲染帧率，18fps 意味着视频卡」——**这个说法不够准确**。

8 路那档的实测：

- **合成到画布**：`视频帧合成调用_采样区间 = 464` → 每路每秒约 **19 帧**
- 每路 `progressDeltaSeconds` 完全一致（3.3004），**没有任何一路在时间上落后**

**所以准确的说法是：视频播放速度是对的，但每秒有约 30% 的已解码帧根本没被画到画布上。**
用户看到的不是「变慢」，是「变顿」——这是流畅度损失，不是失同步。

DOM 侧不存在这个环节：解码帧由浏览器合成器直接上屏，不经过我们的 `drawImage`。

##### 🔴 发现二：两侧的 viewport 根本不一样，之前的对比**仍然不成立**

| | DOM | Leafer |
|---|---|---|
| viewport | 1024 × **700** | 1024 × **1400** |
| view | 960 × **600** | 960 × **1300** |

**Leafer 的可视区高度是 DOM 的两倍多。**

8 个 460×260 的节点：DOM 的 960×600 里最多同时可见约 4 个，
而 Leafer 的 960×1300 里 **8 个全部可见**。

**浏览器对视口外的 `<video>` 有很强的优化**——不可见的元素可能根本不参与合成。
所以 DOM 那组 8 路，很可能实际只合成了约一半。

**结论：DOM 的数字是偏乐观的，两侧至今没有真正同题跑过一次。**
我此前基于这组数据写的倾向性判断，**证据强度不足以支撑**。

##### 但这里有个反直觉的地方，值得单独说

「视口外不合成」**不是 DOM 在测试里作弊，而是它在真实使用中的一项真实优势**。
用户的画布上本来就会有大量节点在视口外，DOM 免费获得这项优化，
**而 Leafer 要自己实现视口裁剪才能拿到同等收益**（我们目前没做）。

所以正确的做法不是「把 DOM 的视口调大来公平比较」就完事，而是**两组都要有**：

1. **同题最坏情况**（两侧都 960×1300，8 个全可见）—— 比的是渲染管线本身
2. **真实场景**（两侧都 960×600，部分节点在视口外）—— 比的是「加上各自的优化后」

**已排任务：DOM 侧按 960×1300 重跑一次，补齐第 1 组。**

#### 真实场景长什么样

用户描述的不是「画布上摆几个视频」，而是**一棵很大的节点树**：

> 1000 个节点，混着视频、图片、**音频**。
> 素材侧是「人物图 + 场景图 + 道具图 + 音乐素材 + 人声素材」，
> 用这些一起生成视频 `v1` —— **于是这些素材节点每一个都连一条线到 `v1`**。
> `v1` 再连到 `v2`，如此往下。

这个拓扑有两个特征，我们既有的基准**一个都没测**：

| 特征 | 既有基准 | 真实场景 |
|---|---|---|
| 节点数量 | **8** | **100 / 1000** |
| 连线密度 | 每个生成单元 1–2 条 | **一个节点可能扇入 100 条** |
| 素材类型 | 图 / 视频 | 图 / 视频 / **音频（尚无此节点类型）** |

#### 🔴 因此 §8.3 的结论要加一句限定

**§8.3「推荐 DOM」是在「视频并发」这一个维度上测出来的，不覆盖节点数量。**

而节点数量恰恰是 **DOM 传统上的弱项**：1000 个节点意味着 1000+ 个 DOM 元素
参与布局与合成，这正是 Canvas 方案通常反超的地方。

**所以在规模基准跑出来之前，§8.3 的推荐只能算「视频维度上的推荐」，不是最终选型。**
两个维度都测完才能定。

#### ✅ S1 + S2 首轮结果（2026-08-05，两侧参数严格一致）

`viewport 1024×1400 / view 960×1300`、节点 `120×80`、采样窗口 3000ms、长帧阈值 50ms。
两侧 `visibleNodeCount` 均为 91（100 节点档为 28），**同一裁剪条件**。

| 场景 | DOM 首屏 | DOM 拖拽 | DOM 缩放 | Leafer 首屏 | Leafer 拖拽 | Leafer 缩放 |
|---|---|---|---|---|---|---|
| 100 节点 | **9.4ms** | 60.13 | 60.12 | 23.4ms | 60.17 | 60.19 |
| 1000 节点 | **18ms** | 60.25 | 60.17 | 27.9ms | 60.09 | 60.13 |
| 1000 + 扇入 100 条 | **16ms** | 60.21 | 59.90 | 24.2ms | 60.04 | 60.14 |
| 1000 + 分散 1000 条 | **19.5ms** | 59.24（长帧 1） | **60.19** | **41.9ms** | 60.20 | **53.80** |

##### 读出来的两条

1. **DOM 首屏每一档都快 2 倍以上**（9.4 vs 23.4 / 18 vs 27.9 / 19.5 vs 41.9）。
2. **连线是 Leafer 的敏感项**：1000 条分散连线时它的缩放掉到 53.80、首屏 41.9ms，
   而 DOM 分别是 60.19 与 19.5ms。扇入 100 条两侧都无感 —— **痛点在连线总数，不在扇入密度**。

拖拽两侧都稳在 60fps，**1000 节点这一档谁都没崩**。

##### 🔴 这组数据的适用边界（别当成「1000 节点无压力」）

**1000 个节点全部挂载，但只有 91 个落在可见裁剪区内**，其余被视口裁掉。
所以测的是**真实场景**（真实画布上大部分节点确实在视口外），
**不是最坏情况**（缩到很小、1000 个同时可见）—— 而那正是 DOM 该吃亏的地方，尚未测。

#### 🔴 S3 · 10000 节点真实文档实测（2026-08-05）—— 17 秒才可交互

前面 S1/S2 用的是探针自造的**纯 `box`** 场景。这一档换成**真实文档**：
用 `createScaleFixture` 生成 10000 节点 + 多对多连线，存进库（**4.62 MiB**），
再用真实浏览器打开 `/canvas/<id>` 量。

| 指标 | 结果 |
|---|---|
| DOMContentLoaded | 1028 ms |
| `canvas-host` 出现 | 2160 ms |
| **可交互（`history-ready`）** | **17181 ms** |
| 挂载 fw 节点 | 10001 |
| **页面 DOM 元素总数** | **135,174**（平均每节点 13.5 个） |

**S1 里 1000 节点首屏 18ms，这里 10000 节点 17 秒 —— 不是 10 倍，是近千倍。**
说明有超线性因素。拆解 DOM 组成后定位到四条，**全部可修**：

| 元素 | 数量 | 问题 |
|---|---|---|
| `<style>` | **6,001** | **每个生成单元注入一份**。应当只有一份共享样式表 |
| `<button>` | **18,011** | 6000 个 hover 工具条 × 3 按钮。**hover 才可见，却全部提前渲染** |
| `<video>` | **2,000** | 全部挂载且 `preload="metadata"`，2000 个视频同时探元数据 |
| SVG（`g`/`path`/`circle`） | **71,104** | 连线层约 17,776 条线 × 4 元素，**占总量一半以上** |

##### ⚠️ 这同时推翻了 S1/S2 的一个隐含前提

S1/S2 用纯 `box` 节点测出的「1000 节点 18ms 首屏、60fps」，
**测的是最好情况**——没有生成单元、没有工具条、没有 per-node `<style>`、没有视频。
**真实内容的每个节点要贵一个数量级。** §8.4 上面那组数字必须按此重新解读。

##### 保存链路：撑得住，但节奏对不上

`PUT` 4.62 MiB → **HTTP 200，1057 ms**；`GET` **128 ms**。体积本身不是问题。

**但自动保存的防抖是 800ms，而一次保存要 1057ms。**
在万节点画布上编辑时，保存请求会持续排队重叠 —— 这是独立于渲染器的架构问题，
需要另行处理（增量保存 / 拉长防抖 / 保存期间不重入）。

#### 🔴 交互层的对照代价 —— 两侧都放弃了原生命中测试

用户 2026-08-05 观察到「Leafer 的交互不是走 leaferjs 自带的，而是外层 HTML 做的」。**属实，且是有意为之：**

| | 实际用的 |
|---|---|
| 指针事件 | `container.addEventListener` + `window` 上的 move/up，**不是 Leafer 事件系统** |
| 命中测试 | `core` 的 `hitTestPoint` 纯函数，**不是 Leafer 内建拾取** |
| 内建手势 | **主动关闭**，`builtin-gesture-guard.ts` 有挂载时断言强制它保持关闭 |

**理由是 parity**：若 Leafer 用自己的拾取与手势、DOM 用浏览器事件，两侧行为会分叉，
对照就失去意义 —— 我们要比的是**渲染**，不是各自的事件系统。

##### 但它有代价，记在这里免得以后误读基准

1. **DOM 侧本可白拿浏览器的 `event.target`**（免费、已优化）—— 没用
2. **Leafer 侧本可用场景图的空间结构** —— 也没用
3. 两边统一走我们自己的 O(N) 树遍历 —— `selectableHit` 里**一次命中是 3 次全树遍历**
   （`hitTestPoint` 一次 + `findNodeById` 两次），1 万节点上即 3 万次节点访问

##### 含义

**对照本身成立**——交互成本两侧完全相同，不影响 DOM 与 Leafer 之间的差值。

**但两侧都没跑在自己的天花板上。** 若日后定下只用一个渲染器，
「用它原生的能力」就不再是作弊，两边都还有余量可挖。

⚠️ 这是 §8.3 的又一条适用边界，与「只测了视频并发、没测节点数量」同类。

#### 待补的规模基准（G5-1 扩展）

| # | 测什么 | 为什么 |
|---|---|---|
| S1 | 100 / 1000 节点的**首屏耗时、拖拽帧率、缩放帧率** | 最基本的规模曲线 |
| S2 | **连线单独成一档**：1 个节点扇入 100 条 vs 分散 1000 条 | 连线是独立的性能项，不能混在节点里一起测 |
| S3 | 混合负载：1000 节点里含 N 个视频同时播 | 两个维度叠加才是真实情况 |
| S4 | **视口裁剪的收益**（两侧都要） | DOM 从浏览器免费拿一部分，Leafer 要自己写 —— 这直接影响规模曲线 |

**证据要求同前**：只报 fps 不采信，必须带「东西真的在变」的证据。

#### 由此产生的三个功能缺口

| 缺口 | 说明 |
|---|---|
| **`audio` 节点类型** | `SHAPE_TYPES` 目前只有 `frame`/`box`/`img`/`video`/`ai-image`/`ai-video`，**没有音频**。而用户的素材里明确有「音乐素材 + 人声素材」 |
| **连线显隐开关** | 1000 节点、上千条线时，连线会淹没画面。必须能整体隐藏 |
| **左下角缩略图（minimap）** | 大树里没有它就迷路 |

##### ⭐ minimap 有个值得注意的点

**缩略图本身几乎必然是 Canvas 或 SVG**——它是一张缩放后的总览图，
用 DOM 画 1000 个缩小的节点毫无意义。

所以**即便主画布选了 DOM，minimap 这一块也会是 Canvas**。
这与 tldraw 的切法一致（图形在 DOM，overlay 在 canvas），
**说明「DOM 还是 Canvas」未必是非此即彼的单选题**，
真实答案可能是「主画布 DOM + 特定图层 Canvas」。

### 🔴 8.3 选型结论（初稿，基于同题实测）

> ⚠️ **先读 §8.4**：本结论只覆盖「视频并发」维度，**未覆盖节点数量维度**。

#### 最终对照（两侧同为 `960×1300`、8 个 460×260 节点、3 秒窗口、全部 muted）

| 并发 | **Leafer** rAF | 长帧 | **DOM** rAF | 长帧 |
|---|---|---|---|---|
| 1 路 | 60.18 | 0 | 60.14 | 0 |
| 4 路 | **52.24** | 0 | 30.89 | 0 |
| 8 路 | 18.01 | **29** | **30.09** | **0** |

#### 但 rAF 不是要看的那个数。真正要看的是「解码了多少帧、画出来多少帧」

| | 每路每秒解码 | 每路每秒真正上屏 | 丢失 |
|---|---|---|---|
| **Leafer 4 路** | ~25 | ~50（同帧重绘） | **0** |
| **Leafer 8 路** | ~27.5 | **~19** | **约 30%** |
| **DOM 4 路 / 8 路** | ~25 | 由合成器直接上屏 | **~0**（逐路 `droppedFrames` 全 0，仅一路为 1） |

**Leafer 的转折点在 4 路和 8 路之间。** 4 路时它把每一帧都画了出来（rAF 52fps 甚至重绘同帧）；
8 路时 rAF 掉到 18fps，而源片是 27.5fps —— **约 30% 的已解码帧根本没被画上去**。

DOM 侧没有这个环节：解码帧由浏览器合成器直接上屏，不经过我们的 `drawImage`。

#### 结论

**推荐 DOM。**

理由不是帧率高 —— **4 路时 Leafer 的 rAF 是 DOM 的 1.7 倍**，那一档 Leafer 明显更流畅。
理由是**两侧的失败模式不对等**：

| | 负载升高时会发生什么 |
|---|---|
| **Leafer** | **视频本身开始丢帧**（8 路丢 30%），因为视频渲染和应用渲染是同一个循环 |
| **DOM** | **只有我们自绘的 UI 变慢**（选中框、拖拽反馈掉到 30fps），视频始终由合成器按原速上屏 |

对一个 AI 生成画布来说这两者严重性差得很远：
用户可以接受拖拽时轻微不跟手，**但生成出来的视频播放起来是卡的，会被直接理解成生成质量有问题**。

而且这是**架构性的**，不是调优能抹平的 —— 只要视频要经过 `drawImage` 进画布，
应用渲染循环的任何压力都会直接转嫁到视频画面上。

#### 选 DOM 要一并接受的账

1. **原生控件夺走命中测试控制权**（见 §8.2 四条隐藏代价）—— 已用「画布优先 + 激活态」绕开，
   代价是进入激活的那次点击被消费，用户实际要点第三次才能操作播放控件。
2. **4 路以内 Leafer 的自绘 UI 更流畅**（52 vs 31 fps）。DOM 的 30fps 拖拽手感是否可接受，
   **机器测不出来，必须人去拖一遍**。这是唯一还需要人判断的一项。

#### 仍未测到的（不要当成已知）

- **内存两侧都是空白**。页面级 API 测不到视频解码缓冲与 GPU 显存，
  `performance.memory` 只有 JS heap。要真数据必须读 Chrome Task Manager 进程内存。
- **每档只跑了一次**，没有重复采样，方差未知。
- **只在 Headless Chromium 上测过**，没有真实有头浏览器、没有其他内核。
- **Leafer 未实现视口裁剪**。如果实现了，8 路里视口外的部分可以不画 ——
  这是 Leafer 尚未兑现的一张牌，会缩小差距但不改变「视频与应用渲染耦合」这条根本属性。

#### 与另外两条独立证据同向

- ComfyUI 在完全相同的场景（AI 生成节点画布）里**从 Canvas 反向迁往 DOM**
- 调研过的所有库中**没有一个趟过「节点内嵌视频播放器」这条路**

##### 此前的倾向性判断（已被上面的实测取代）

**倾向 DOM。** 理由不是帧率数字本身 —— 4 路时 Leafer 还赢 ——
而是**「视频播放不经过我们的渲染循环」这条架构属性**，它在负载升高时保护了最关键的体验，
而这一点在 Canvas 方案里无法通过优化获得。

这与另外两条独立证据同向：
ComfyUI 在完全相同的场景里从 Canvas 反向迁往 DOM；
以及调研过的所有库中没有一个趟过「节点内嵌视频播放器」这条路。

**代价那一侧也要记住**：DOM 的原生控件夺走了命中测试控制权
（见上文四条隐藏代价），这是选 DOM 要一并接受的账。

规则：

- **耗时如实记**，包括踩坑返工的时间。这张表失真了，整个项目就白做。
- **一侧做不到**时也记一行，写清技术原因——那是最有价值的条目。
- 每引入一个 `leafer-*` 插件，**单独核 license 并登记进 §6 依赖表**（主仓 MIT 不能外推到周边包）。

### 9.4 借鉴清单：抄什么，不抄什么

gzm-design 是个成熟编辑器，好东西很多，**但它是单渲染器的通用设计器，我们是双渲染器的选型验证项目，目标不同**。全盘照搬会把它的复杂度整个继承过来。逐项定性：

⚠️ **本表 2026-08-03 按主要矛盾（`AGENTS.md` §1.1）重新定过性，比初版更严。** gzm-design 是**通用设计器**，它的多数模块服务的是「把图形调得更好看」——那正是本项目明确不做的方向。初版把 `clipboard` / `contextMenu` / `layer` 一并列为「借鉴落 core」，那是在往设计器漂，已降级。

| 模块 | 行数 | 判断 | 理由 |
|---|---|---|---|
| `app/editor/zoom.ts` | ~35 | ✅ **借鉴逻辑，落 `core`** | 缩放平移是看生成结果的基本操作，业务需要 |
| `core/undoRedo/*` | ~150 | 🟡 **只借思路，不借实现** | 我们的撤销是**持久化**的（存后端、以 documentId 为键、窄操作日志，见 `domain.md` §4.5），与它的内存命令栈形态不同。可借「操作可逆」的建模思路，别搬命令栈代码 |
| `core/shapes/*` | ~370 | ✅ **借鉴模式，不照抄代码** | 见 §10——它是 Leafer 专属扩展，我们要三段式。**但只用在 img/video 上**，不用来长图形编辑 |
| `core/canvas/mLeaferCanvas.ts` | 571 | 🟡 **只能进 `renderer-leafer`，且只取需要的部分** | 纯 Leafer 封装。**绝不能进 `core`**，否则 `core` 被 Leafer 污染，DOM 侧没法用 |

## 10. 自定义 shape 的三段式结构

### 10.1 gzm-design 的做法，以及为什么我们不能照抄

gzm-design 的自定义元素（`QrCode` / `BarCode` / `HTMLText2` / `Image2`）是**纯 LeaferJS 扩展**：

```ts
@registerUI()
class QrCode extends Rect {
  @dataProcessor(CustomData) declare public __: ICustomData
  @boundsType('文字') declare public text: string
  public get __tag() { return 'QrCode' }
  public __onUpdateSize() { this.renderQr(); super.__onUpdateSize() }
}
```

数据侧存 `tag: 'QrCode'` + 参数，Leafer 靠 `registerUI` 反查类实例化。**在单渲染器项目里这个设计很干净**——数据驱动、类型自注册、参数变更自动触发重绘。

但它整套依赖 `registerUI` / `dataProcessor` / `boundsType` / `__tag` / `__onUpdateSize`，**这些只在 Leafer 世界存在**。DOM 侧一个都没有。照抄进 framewright 会让 `renderer-leafer` 有 shape 而 `renderer-dom` 无从对齐，直接违反「两版同步」。

还有一个更说明问题的例子：`Image2` 的存在理由是注释里写的「**解决官方 Image 元素不能在初始化时设置 fill 的 opacity 问题**」——这是个纯粹的 **Leafer workaround**，DOM 侧压根没有这个问题。**它证明了 shape 层不可能 1:1 对应**，硬对应反而是错的。

### 10.2 framewright 的三段式

把一个 shape 拆成三段，其中**只有第三段要写两遍**：

| 段 | 位置 | 内容 | 写几遍 |
|---|---|---|---|
| **① 数据** | `packages/core/src/node-schema.ts` | `fwType` 取值 + 该类型的参数字段（如 QR 的 `text`/`ecLevel`/`logo`） | 1 |
| **② 纯逻辑** | `packages/core/src/shapes/<name>.ts` | 参数 → **可绘制的中间产物**，渲染器无关 | 1 |
| **③ 渲染绑定** | `renderer-leafer/src/shapes/<Name>.ts`<br>`renderer-dom/src/shapes/<Name>.tsx` | 把中间产物挂进各自的渲染树 | 2（都很薄） |

以二维码为例：`QRCode.toString(text, options) → SVG 字符串` 这一步**完全与渲染器无关**，属于 ②，只写一遍。剩下的 ③ 两侧各自是「Leafer 里把 SVG 设成 `fill`」和「React 里渲染一个 `<img>`/内联 SVG」——都只有几行。

这正是 §9.2 那条规律的具体实例：**要写两遍的永远只有「挂进渲染树」那一薄层。**

### 10.3 shape 注册表：把「两版同步」变成机器可检查

`core` 导出全部合法 `fwType` 的清单；两个渲染器各自维护 `fwType → 实现` 的注册表。

**应用层在装载渲染器时校验注册表完整性**：某个渲染器缺任何一个 `fwType` 就**当场报错**，而不是渲染时静默画不出来。

```
core.SHAPE_TYPES            = ['frame','box','img','video', ...]
rendererDom.shapes          → 必须覆盖 SHAPE_TYPES 全集
rendererLeafer.shapes       → 必须覆盖 SHAPE_TYPES 全集
```

**这条的价值超出技术本身**：`conventions.md` §4.3 的「两版同步开发、不许单侧先行」原本只是一条纪律，靠人自觉；有了注册表完整性检查，**它变成加一个 shape 就必须两边都加、否则跑不起来的硬约束**。纪律靠机器守，比靠人守可靠。

允许一侧显式声明「不支持」——注册一个显式的 unsupported 实现（渲染成占位并上报），而不是留空。这样「做不到」是**被记录的**，正好喂给 §8.2 的实现成本对照表。

## 11. 无限画布与交互契约（P2 范围，契约在 P0 收尾时定）

### 11.1 交互规格

> **单一真相源 = [`docs/interaction-spec.md`](interaction-spec.md)。本节不重复列举，避免两份漂移。**

那份规格按 Figma / 即梦 / liblib canvas 的通用习惯**直接定死**——这些是行业约定、用户已有肌肉记忆，**不要创新、不留给实现者发挥**。两个渲染器照同一份规格实现，否则画出来的差异是「没对齐规格」而不是「渲染方案差异」，会污染选型结论。

本节只强调三条与架构直接相关的：

- **选中粒度恒为业务单元**，永不选中内部元素——由 §2.2 的节点粒度原则天然保证，不需要额外抑制逻辑。
- **拖拽过程是纯呈现**，预览由渲染器自己画、不更新 node 树，只在松手时提交一次。
- **描边与控制点不随缩放变粗细**，需按 `1 / viewport.scale` 反向补偿，两侧都要做。

### 11.2 ⭐ 关键结论：交互的「计算」几乎全在 core，渲染器只负责「感知输入」与「画出反馈」

这是 `docs/lessons.md` #9 那条规律在交互上的应用，而且比预想的更彻底：

| 环节 | 属于谁 | 为什么 |
|---|---|---|
| 监听中键 / 滚轮 / 拖拽手势 | **渲染器** | DOM 与 Leafer 的事件系统不同，只能各写 |
| **屏幕坐标 ↔ 画布坐标换算** | **`core`** | 纯数学，与渲染方式无关 |
| **以光标为锚点的缩放计算** | **`core`** | 纯数学 |
| **框选矩形与节点的相交判定** | **`core`** | 纯几何，`walkTree` 已有绝对坐标 |
| 画出选框、选中高亮、拖拽预览 | **渲染器** | 视觉表现，各写 |
| 更新 viewport / selection / node 树 | **应用层** | 渲染器永不直接改状态 |

因此 `core` 新增两个纯 TS 模块（P2 引入）：

- `core/src/viewport.ts` —— `screenToCanvas()` / `canvasToScreen()` / `zoomAtPoint(viewport, screenPoint, deltaScale)` / `panBy()`
- `core/src/hit-test.ts` —— `hitTestPoint(root, canvasPoint)` / `hitTestRect(root, canvasRect)`，都返回业务单元的 `fwId` 列表

**两个渲染器共享同一套几何**，从根上杜绝「框选在 DOM 侧选中 5 个、Leafer 侧选中 4 个」这类分叉。

### 11.3 回调契约

> 下面是定案前的草案，**已被两侧独立作答推翻多处**（坐标系语义、缺两个回调、频率未定义），保留作对照。

<details>
<summary>草案原文（已作废，勿据此实现）</summary>

（语义层，绝不上抛原生事件）

`RenderContext` 增加 `callbacks`。**全部是语义，不是事件**——渲染器负责把「中键拖了 30px」翻译成「视口平移到 X」，上层不知道也不该知道用户用的是中键还是空格：

```ts
export type SelectionMode = 'replace' | 'toggle' | 'add'

export interface RendererCallbacks {
  /** 用户改变了选中集。fwIds 恒为业务单元，不含内部元素 */
  onSelectionChange(fwIds: readonly string[], mode: SelectionMode): void
  /** 用户把若干节点移动到了新位置（画布坐标，拖拽结束时触发一次，不是每帧） */
  onNodesMove(moves: ReadonlyArray<{ fwId: string; x: number; y: number }>): void
  /** 用户改变了视口（平移或缩放皆走此回调） */
  onViewportChange(viewport: Viewport): void
  /** 用户激活了某个节点（双击），上层决定打开生成面板还是别的 */
  onNodeActivate(fwId: string): void
}
```

**`onNodesMove` 在拖拽结束时触发一次**，不是每帧——每帧回调会让每次拖拽产生几百条撤销日志（`domain.md` §4.5）。拖拽过程中的预览由渲染器自己画，那是纯呈现，不进状态。

</details>

### 11.4 为什么契约要在 P0 收尾时定，而不是等 P2

P0 的目的是夹逼接口，而**交互恰恰是接口里最容易被单一实现带偏的部分**（DOM 有事件冒泡与 CSS 命中测试，Leafer 有自己的事件系统与命中检测，差异最大）。

现在两个渲染器都已完成并在手上，是定交互契约最便宜的时刻——两边的实现者都能立刻回答「这个回调我这边给得出来吗」。等到 P2 开工才定，等于把最难的接口决策推到最贵的时候做。

**但契约只写文档、不写实现**，交互代码仍属 P2。这不算扩大 P0 范围。

### 🔴 8.5 S3 两侧同题对照（2026-08-05）—— **裁剪抹平了规模差距**

两侧同参数（`viewport 1024×1400 / view 960×1300`、采样窗口 3000ms、长帧阈值 50ms），
**且数据同源**：都用 `core` 的 `createScaleFixture({ seed: 7 })`，
所以测的就是用户能在页面上打开看的那一份。

#### 裁剪效果（两侧一致，说明共用的判定生效了）

| 场景 | 逻辑节点 | **实际挂载** | 挂载率 | 连线 |
|---|---|---|---|---|
| 1000 many-to-many | 1000 | **170** | 17.0% | 360 / 1776 |
| 10000 many-to-many | 10000 | **170** | **1.7%** | 367 / 17776 |
| 10000 none | 10000 | **170** | 1.7% | 0 |

#### 交互帧率

| 场景 | 操作 | **DOM** | **Leafer** |
|---|---|---|---|
| 1000 m2m | 拖拽 / 缩放 / 平移 | ~60 / ~60 / ~60 | 58.71 / 44.21 / 47.24 |
| **10000 m2m** | 拖拽 | 54.37 | 56.48 |
| | 缩放 | 37.13 | 34.22 |
| | **平移** | **31.81**（p95 50.0、max 66.7） | **39.91**（p95 44.6、max 54.7） |
| 10000 none | 拖拽 / 缩放 / 平移 | ~60 / ~60 / 57.02 | 55.38 / 41.78 / 55.63 |

#### 读出来的三条

**1. 裁剪之后，节点规模不再是决定性维度。**

裁剪前 DOM 在 10000 节点上直接卡死（13.5 万元素、2.4GB、17 秒可交互）；
裁剪后两侧都可用，互有胜负 —— Leafer 平移略好（39.91 vs 31.81），
DOM 首屏略好。**没有一边崩掉。**

**2. 🔴 连线是两侧共同的主要成本，而且远超节点本身。**

同为 10000 节点，仅「有无连线」之差：

| | DOM 平移 | Leafer 平移 |
|---|---|---|
| 10000 **无连线** | **57.02** | **55.63** |
| 10000 **多对多连线** | **31.81** | **39.91** |

**平移帧率掉了约一半，而节点数完全相同。**
挂载的连线只有 367 条（占 17776 的 2%），仍然是最大开销 ——
说明成本在**曲线求解与重绘**，不在数量本身。

→ 这让「连线显隐开关」从 UX 需求升级为**性能杠杆**。

**3. 首屏数字不要直接比。** 两份报告都主动标注了口径问题：
Leafer 侧 1000 档等了 3 帧才拿到像素证据、两个 10000 档只等 1 帧；
DOM 侧首屏为单次采样。**不应把「档位越大首屏越快」解读成规模优势**，
那是采样口径造成的。两边都没有拿这个数字往有利方向讲。

#### 这对选型意味着什么

**规模维度原本是 DOM 的软肋，裁剪补上后已经拉平。**
于是**视频维度重新变回决定性的那一维** —— 在那一维上：
8 路并发时 Leafer 丢约 30% 的已解码帧（视频渲染与应用渲染同一循环），
DOM 的视频由合成器独立上屏、不丢帧，且这是架构性差异、调优抹不平。

⚠️ 但**默认渲染器目前是 LeaferJS**（用户 2026-08-05 决定，当时 DOM 侧尚未接裁剪）。
裁剪已让前提改变，**是否改回 DOM 需要用户重新判断** —— 这属于范围决策，不由编排方定。

### 🔴🔴 8.6 S4 缩小档（2026-08-05）—— **§8.5 的结论只在接近 100% 缩放时成立**

用户指出 S1–S3 的测试设计不严谨：「缩放比例可能较大，如果 10% 将卡死」。
**实测证实，且比预想严重。** 编排方早在 §8.4 标注过「最坏情况尚未测」，但一直没做。

#### 挂载量随缩小暴涨（10000 节点 many-to-many）

| scale | 挂载节点 | 挂载率 | 挂载连线 | DOM 元素数 |
|---:|---:|---:|---:|---:|
| 100% | 170 | **1.70%** | 367 | 2,061 |
| 50% | 660 | 6.60% | 1,294 | 7,483 |
| 25% | 2,535 | 25.35% | 4,803 | 27,914 |
| **10%** | **9,600** | **96.00%** | **17,587** | **102,987** |

#### 帧率

| scale | DOM 拖拽 | DOM 平移 | Leafer 拖拽 | Leafer 平移 |
|---:|---:|---:|---:|---:|
| 100% | 58.01 | ~58 | ~58 | ~58 |
| 25% | 24.20 | — | — | — |
| **10%** | **6.13**（max 300ms） | **2.57**（max 616.6ms） | **0.53**（max 2948.1ms） | **0.56**（max 2705.2ms） |

**Leafer 在 10% 下是 0.53 fps —— 两秒一帧，彻底不可用，比 DOM 差约 10 倍。**

#### 🔴 两条必须记住的

**1. 差异纯来自渲染代价，不是裁剪集合不同。**
执行方核对过：两侧每档的挂载节点数与连线数**完全一致**。
所以这是 `core` 的裁剪**策略**问题，不是某个渲染器实现得差。

**2. 面积裁剪本身有天花板。**
视口覆盖的画布面积随缩放**平方**增长，而裁剪按面积算 ——
**缩到 10% 就等于没裁**。这不是实现 bug，是策略的固有上限。

#### 这推翻了 §8.5 的核心判断

§8.5 写「裁剪抹平了规模差距」，**那只在接近 100% 缩放时成立**。
而「缩小看全局」恰恰是大画布最常用的操作之一 —— 两侧在那里都垮了。

#### 修复方向（已排任务）

| 层 | 做法 |
|---|---|
| **挂载数上界** | 给裁剪加 `maxNodes`，超出时按「距视口中心距离」取最近的 N 个 —— 用户注意力在中心，边缘缺失最不易察觉 |
| **LOD 细节层级** | 按 scale 给出 `full` / `simplified` / `dot` 三档。10% 下一个 120×80 的节点只有 **12×8 像素**，画素材、文字、控件全是浪费 —— 那个尺寸下人眼只能看见色块 |
| **连线上界与降级** | 10% 下 17,587 条连线各自求解贝塞尔是主要开销之一；低细节层级下退化为直线甚至不画 |

阈值不拍脑袋，用实测反推：100% 时 170 个跑 58fps、25% 时 2535 个掉到 24fps、
10% 时 9600 个掉到 6fps（DOM）。

### ✅ 8.7 LOD 与挂载上界落地（2026-08-05）—— 10% 档两侧均恢复 60fps

#### 策略（`core`，两侧共用）

| 机制 | 取值 | 依据（全部由实测反推，非拍脑袋） |
|---|---|---|
| `maxNodes` | **1500** | 不贴着已知失速点 2535 取值，留 40% 余量；仍是 100% 流畅样本（170）的 8.8 倍 |
| `maxConnections` | **1000** | 是流畅样本 367 的 2.7 倍，但把最坏样本 17,587 压到 **5.7%** |

触顶时按**距视口中心的平方距离**取最近项 —— 用户注意力在中心，边缘缺失最不易察觉。
两处容易写错的细节都处理了：**连线排序发生在贝塞尔求解之前**（否则是「先解 17,587 条再截断」）；
**嵌套节点的祖先 frame 连同保留并计入同一上限**（否则会出现「子节点在集合里但父节点没挂载，画不出来」）。

| | 改前 | 改后 |
|---|---|---|
| **DOM** 10% 拖拽 | 6.13 fps | **60.00 fps** |

| **Leafer** 10% 拖拽 | 0.53 fps（max 2948 ms） | **60.03 fps**（max **22.6 ms**） |
| **Leafer** 10% 平移 | 0.56 fps | **52.62 fps** |

Leafer 侧是 **113 倍提升、最大帧缩短 130 倍**。

| 变化 | 归因 |

| DOM 25% 挂载连线 `0 → 1000` | ✅ **仪器修复**（选择器只认 `path`，而 simplified 档画的是 `<line>`） |

#### 新增的仪器纪律

DOM 侧现在同时记录 `connectionLayerPresent` 与 `mountedConnectionElementTypes`，

这与本仓反复吃亏的模式同源：「扫描没找到」与「扫描没生效」输出相同、
「测试绿」与「测试没跑」表现相同。**仪器本身也必须能自证。**

### 🔴 8.10 视频播放连续性实测（2026-08-05 夜）—— **只有 DOM 侧丢**

**起因**：React Flow 探针顺带发现「离屏裁剪会卸载 `<video>`，回到视口后从头播」。
我们两侧都做了裁剪 + LOD，**但此前从未测过**。

**探针设计上有一处必须分清**（执行方在上一轮主动指出，编排方给任务时没想到）：
`preload="none"` 是我们在 DOM 结构瘦身时**主动设的**（阻止 2000 个视频同时探元数据，
见 `a5f2754`）。所以「重挂载的 `<video>` 不会自动 ready」是**我们的设计**，不是连续性缺陷 ——
**不能把懒加载语义混进连续性结论**。

因此时序改为：回到视口后**先抓即时快照**，再主动 `play()`，据此把两件事分开：
**会话状态是否丢失** vs **新媒体元素能否重新加载**。

#### 结果

| 渲染器 | 档位 | 元素重建 | **播放位置保留** | 暂停态保留 | `play()` 成功 | 加载恢复 |
|---|---|---|---|---|---|---|
| **DOM** | culling / simplified / dot | ✅ 重建 | ❌ **丢失** | ❌ 丢失 | ✅ | ✅ |
| **Leafer** | culling / simplified / dot | ❌ 不重建 | ✅ **保留** | ✅ 保留 | ✅ | ✅ |

DOM 侧三档全部从 `currentTime ≈ 0.2205s` 归零、`readyState` 由 4 掉到 0。

**Leafer 不丢的原因**：视频由 `VideoSource` 持有，裁剪只摘 Leafer 实例、不销毁媒体元素。

#### 关键区分

`playCallSucceeded = true` 且 `mediaBecameReadyAfterPlay = true` ——
**新元素能正常加载，丢的纯粹是会话状态**。
若不做这个区分，很容易把 `preload="none"` 的懒加载误判成「视频坏了」。

#### 裁定：播放位置属会话状态，由 host 持有

依据本仓铁律 —— **状态不许存在渲染器内部**。播放位置与播放状态和
`viewport` / `selection` 是同一类东西：它们跨渲染器切换必须保留（今天已经能切
`Leafer ↔ DOM`，切换后视频从头播是同样的问题）。

**做法**：host 记录每个视频节点的 `currentTime` 与 `paused`，
渲染器重挂载时按此恢复。⚠️ 三档 LOD 都要覆盖 —— `simplified` / `dot` 根本不画视频内容。

⚠️ **不要用「让 DOM 侧也别销毁元素」来解决**：那会把 2000 个 `<video>` 常驻回来，
正是 §8.4 里 13.5 万元素 / 2.4GB 的成因。**保留状态，不保留元素。**

## 12. 视口裁剪的三次修正（2026-08-05）

### 12.1 保留区为什么从圆改成矩形

用户在极限缩放下**肉眼看到保留区是一个圆形**（原话「有点像我的世界」）。
这不是错觉：`maxNodes` 溢出时按 `deltaX² + deltaY²` 排序保留最近的，
这个度量各向同性，等值面必然是圆盘。

而视口是矩形（约 16:9）。用圆盘去填矩形预算，要覆盖矩形四角就必须让半径
大到能罩住对角线，于是上下方向大量预算落在视口外 —— **花了预算却看不见**。

改成按视口半宽/半高归一化：`max(|dx|/halfW, |dy|/halfH)`。
等值面变成与视口同宽高比的矩形，同样预算覆盖更多真正可见的区域。

⚠️ **测这条要用宽扁视口**。正方形视口下两种度量等价，测不出差别 ——
用正方形视口写的测试会绿，但什么都没验证到。

### 12.2 裁剪预算为什么进 `RenderContext`

`maxNodes` / `maxConnections` 要开放给用户按本机性能调，就必须让两侧渲染器都读到。
执行方在这里正确地停下来升级了阻塞：host 持有配置和渲染器用上配置之间**没有合规通道**，
剩下的只有 core 模块级可变全局 —— 那会同时违反「状态归 host」和多实例安全。

**裁决：扩 `RenderContext`。** 理由不是「这样最方便」，而是**已有三个先例走同一条通道**：
`viewportSize`、`interactionMode`、`connectionVisibility`。不新开机制，照着它们写。

配套红线：新字段缺省值必须**在没人传的时候就是对的**（1500 / 1000），
要走显式 resolve 函数，并**为「不传时用默认值」单独写测试**。
这条不是空谈 —— `interactionMode` 就因为直接比较 `=== 'unified'`，
`undefined` 落进了 native 分支，而契约文档写的缺省是 unified。

### 12.3 fan 模式：上限只截输出，不截工作量

`fanin` 拓扑下**最后一个节点的 `sourceFwIds` 装着全部其他 9999 个节点**
（见 `scale-fixture.ts`）。而 `getConnectionsInViewport` 的原实现是：

1. 遍历所有连线，**每条都分配候选对象**、算中点、算距离 —— 9999 次
2. 建一个 9999 项的 Set 交给 boundsCache
3. 对 9999 项排序
4. **这才**开始逐条解曲线、做 AABB 相交，直到凑够 `maxConnections` 才 break

所以上限只影响「最终渲染几条」，**完全不影响「算了多少条」**。每次视口变化重跑一遍。
雪上加霜：fanin 下所有线共享目标端点，AABB 几乎裁不掉任何一条，永远顶着上限跑。

#### 关键发现：只用端点就能算出保守 AABB

看 `computeConnectionCurve` 生成的四个控制点：

```
p0 = {from.x,     from.y}
c1 = {from.x + k, from.y}
c2 = {to.x - k,   to.y}      k = clamp(|to.x - from.x| * 0.5, 40, 160)
p3 = {to.x,       to.y}
```

**四个控制点的 y 只有 `from.y` 和 `to.y` 两个取值** —— `k` 只作用在 x 上，且恒 ≤ 160。
贝塞尔曲线含于控制点凸包，于是：

- y 范围**恰好**是 `[min(from.y,to.y), max(from.y,to.y)]` —— 精确，不是估计
- x 范围 ⊆ `[min(from.x,to.x) - 160, max(from.x,to.x) + 160]` —— 保守但足够紧

结论：**不解三次曲线、不分配任何对象**，两个端点就能做早退判定。
把它放在 `candidates.push` 之前，fanin 下绝大多数连线在物化之前就被丢掉。

#### 保守性是独立验证过的，不是推导完就信

早退判定一旦不保守，连线会**静默消失** —— 没有报错，只是画面少了东西，
这类缺陷极难在日常使用中发现。所以编排方另写了一份独立复核：
50 万组随机端点 + 随机视口，对每一个被早退拒绝的连线，
用 200 点密集采样的真实贝塞尔曲线检查是否穿过视口。

**结果：38.8 万次早退，零错杀。**

#### 实测收益（DOM，10000 节点 × fanin，5 次采样取中位数）

| 缩放 | 改前 fps | 改后 fps |
|---|---|---|
| 100% | 46.41 | **59.67** |
| 50% | 32.49 | **44.75** |
| 25% | 38.45 | **43.76** |
| 10% | 59.67 | 59.67 |

10% 档没有变化，因为那一档 LOD 本来就把连线整个裁掉了
（探针记录 `mountedConnectionCount: 0`）。
**真正的痛点是 50% 档** —— 有改善但离 60 仍有距离，说明早退不是全部答案，
元素数量（每条线一个独立元素）仍是待验证的次要主因。

### 12.4 「减少渲染对象数」对 DOM 成立，对 Leafer 不成立

这是本轮最有价值的产出，而且是个**否定结论**。

把同样式连线合并成批量 path（元素数从 N 降到批次数），
直觉上两个渲染器都该受益。实测不是这样：

| 渲染器 | 缩放 | 批量前 | 批量后 | |
|---|---|---:|---:|---|
| DOM | 100% | 46.41 | **59.67** | 有效 |
| Leafer | 100% | 53.12 | 54.68 | +2.9%，基本持平 |
| Leafer | 50% | 20.02 | 22.37 | +11.8%，但最大帧更差 |
| Leafer | 25% | 15.47 | **7.67** | **-50.4%，明确回归** |
| Leafer | 10% | 51.12 | 50.94 | 持平（该档 LOD 本就隐藏连线）|

原因：Leafer 的瓶颈不主要在元素数量。25% simplified 档下，
**巨型 path 的重建、解析与边界计算反而成了热点** —— 合并省下的元素开销，
抵不过单个超大路径带来的解析成本。

#### 三条可复用的教训

1. **一侧的优化收益不能外推到另一侧。** 两个渲染器共享 core 的裁剪策略，
   但渲染层的性能模型是各自独立的。跨渲染器复用优化结论前必须各自实测。
2. **性能优化必须保留「无工作量」对照档。** 10% 档两侧都几乎没变化 ——
   因为那一档 LOD 本就把连线整个裁掉了。如果没有这个对照，
   很容易把「本来就没干活」误读成「优化无效」或「优化有效」。
3. **必须用指纹与实际渲染数量验证。** 否则一个「什么都没渲染」的实现
   会给出最好看的 fps。

### 12.5 连线的 DOM 属性同时服务两件事，不能只顾一件

批量 path 把 DOM 的 `data-fw-connection-from` / `-to` 换成了批次级属性，
连线照常渲染，但**单条连线在 DOM 里不再可定位** —— `e2e/host-interaction.spec.ts`
两条用例由 2 变 0。

这里有个诱人的错误选项：把断言从 2 改成 0，测试立刻变绿。
**那是用假通过掩盖能力回退。** 连线的 hover / 选中 / 删除将来都需要这个抓手。

裁决：**按连线数量分档**。数量低时保留逐条元素
（demo 画布只有 2 条连线，合并省不下任何东西，而可寻址性很重要）；
数量高时才批量合并（此时逐条寻址本来也不是可用的交互方式）。
阈值实测得出。
