> ⚠️ **本文件当前包含大量未定项**，设计尚在 brainstorm 阶段。开环闭合前不要按此搭脚手架。

## 1. 核心命题

> **一份 JSON node 树，两套渲染器，渲染出同一个画布，并且能在运行时一键切换。**

这是本项目存在的理由。所有架构决定都服务于一个可回答的问题：
**做 AI 画布工作台，画布层用 DOM（Next.js/tsx 组件）还是 LeaferJS？**

因为作者事先不知道哪个更好，所以答案不能靠纸面推演，只能靠**并行实现 + 现场对比**。于是「渲染层可插拔、可在线切换」从一个「架构优点」升格成**项目的第一需求**。

架构的第一原则由此确定：**让两个渲染器可以被公平对照，且能在同一份数据上原地互换。** 任何让某一侧「偷跑」的设计（把选中态塞进 Leafer 节点、把视口存在 DOM 容器上）都会同时污染结论、并在切换时当场丢状态。**切换是最好的架构测试仪。**

## 2. 分层

```
            ┌─────────────────────────────────────┐
            │            apps/web (UI)            │  工具栏 / 图层面板 / 属性面板 / 生成入口
            │  ┌───────────────────────────────┐  │  ┌──────────────────┐
            │  │        RendererHost           │◀─┼──│ 渲染器切换开关   │
            │  │  持 container，装/卸 adapter   │  │  └──────────────────┘
            │  └───────────────┬───────────────┘  │
            └──────────────────┼──────────────────┘
                               │  RenderContext（树 + 选中 + 视口 + 回调）
            ┌──────────────────▼──────────────────┐
            │        @framewright/core            │  node schema · 树操作 · 会话状态 · RendererAdapter
            └───────┬─────────────────────┬───────┘
                    │                     │
    ┌───────────────▼──┐              ┌───▼─────────────────┐
    │ renderer-dom     │              │ renderer-leafer     │   ← 两个实现，同一个接口
    │ (React/tsx)      │              │ (LeaferJS)          │      运行时可互换
    └──────────────────┘              └─────────────────────┘

                ┌─────────────────────────────┐
                │   @framewright/provider     │  AI 生成能力接口 + mock 实现
                └─────────────────────────────┘

                ┌─────────────────────────────┐
                │      apps/server (?)        │  持久化 node 树 + 代理生成请求（是否进 MVP 待定）
                └─────────────────────────────┘
```

**边界规则**

- `core` **零渲染依赖**——不 import React，不 import leafer。它是纯 TS。
- 两个 renderer 实现同一个 `RendererAdapter` 接口，互不感知对方存在。
- `apps/web` 只依赖 `core` 与 `RendererAdapter`，**不允许出现渲染器品牌分支判断**；切换渲染器靠注入不同实现。
- `provider` 只定义「怎么发起生成、怎么拿结果」，不含任何具体厂商实现。

## 3. 数据流

```
用户操作（拖动/改属性/新建）
   → 应用层派发一个对 node 树的变更
   → core 更新 node 树（唯一真相源）
   → 通知当前 renderer 重绘受影响子树
   → renderer 把交互事件（点击/拖拽结束）抛回应用层
```

```
用户发起生成
   → provider.submit(params) → 得到 generationId
   → 轮询 / 订阅 status
   → succeeded 时把结果 URL 写成新的 img/video node 挂进树
```

**关键约束**：渲染器**永远不直接修改 node 树**。它只上报「用户想做什么」，改树是应用层的事。这条一破，两个渲染器就会各自长出一套隐式状态，对照实验作废。

## 3.5 运行时切换机制

`RendererHost` 是 `apps/web` 里唯一持有画布 DOM 容器的组件。切换流程：

```
用户点切换开关
  → host 调 当前adapter.destroy()          清空容器、解绑监听、释放实例
  → host 调 新adapter.mount(container, ctx) 用同一份 RenderContext 重新挂载
  → 画面、选中、视口 三者与切换前一致
```

**为什么这样切是安全的**：`RenderContext` 里已经包含了重建画面所需的全部信息（node 树 + 选中集 + 视口）。渲染器是无状态的投影，销毁重建不丢东西。

**两个渲染器都是运行时依赖**（不是构建期二选一），因为要在同一个页面里互换。若包体积成为问题，用动态 import 懒加载未激活的那一个——但**不能**做成构建期开关，那样就切不了。

**已知的最难统一处 = 交互事件。** DOM 有原生事件冒泡与 CSS 命中测试；LeaferJS 有自己的事件系统与命中检测。拖拽、框选、缩放平移这三件事在两侧的实现差异会很大。`RendererAdapter` 的回调契约必须定义在**语义层**（「用户把节点 X 拖到了 (x,y)」「用户框选了区域 R」「用户把视口缩放到 s」），而不是事件层（不要往上抛 `MouseEvent`）。**这一处是整个选型验证里信息量最大的地方，也最可能推翻直觉。**

## 4. 已定选型

| 项 | 决定 | 理由 |
|---|---|---|
| 包管理 | pnpm workspace monorepo | 双渲染器天然需要多包；用户既有栈就是 pnpm |
| 语言 | TypeScript strict | node schema 是本项目的核心资产，必须类型化 |
| 画布方案 | DOM 与 LeaferJS **并行两套** | 这就是要验证的东西本身 |
| 渲染层 | **可插拔 + 运行时一键切换**，非构建期二选一 | 作者事先不知道哪个更好；切换是最好的对照装置与架构测试仪 |
| DOM 侧形态 | React / tsx 组件 | 用户明确要求「html 组件版本 nextjs(.tsx)」 |
| 功能推进 | 两版**同步开发**，不许单侧先行 | 单侧先行 = 对照实验作废，且回头补等于不补 |
| 交互事件契约 | 定义在**语义层**，不上抛原生事件对象 | 两套事件系统无法在事件层统一 |
| MVP 成功判据 | **端到端跑通 + 作品可展示**；选型结论是副产品 | 用户 2026-08-03 确认 |
| 后端 | **完整后端一次到位**：NestJS + Postgres/Prisma + 真实 provider | 用户 2026-08-03 拍板。风险（三条战线）用 §5.1 阶段排序化解，不靠自觉 |
| 布局 | 绝对定位 x/y/w/h | 先跑通；布局引擎见开环 #5 |
| z 序 | 兄弟数组顺序 | 避免 zIndex 与数组顺序两份真相 |
| 元素集 | 只做 frame / box / img / video | 四个足够暴露两个渲染器的差异，多做是浪费 |

## 5.1 阶段排序（防三条战线并行）

「双渲染器 + 完整后端 + 真实生成」三件事一起开工是明确的失败模式。用**排序**而不是自觉来防：

| 阶段 | 目标 | 范围 |
|---|---|---|
| **P0 接口夹逼** | 逼出正确的 `RendererAdapter` 形状 | **两个渲染器同时写，但功能面极小**：只渲染 frame + box，静态，无交互。后端不动。 |
| **P1 骨架贯通** | 端到端一条线跑通 | NestJS + Postgres/Prisma 存取 Document；画布改动能存能读，刷新还在。生成先用 mock provider（提交→轮询→返回占位素材）。 |
| **P2 交互补齐** | 画布真能用 | 拖拽、框选、缩放平移、属性编辑。**两版严格同步**。切换开关此时上线并纳入冒烟。 |
| **P3 真实生成** | 作品完整 | 接真实 provider，img/video 节点接真实素材。 |

**P0 为什么必须两版同时写**：只用一个实现去定接口，定出来的接口必然是偏那一侧的（先写 DOM 就会漏掉 Leafer 的命中检测与坐标系差异，反之亦然）。**接口的正确形状只能靠两个实现从两边夹出来。** 这也正好落实「两版同步开发」，而不是嘴上说说。

P0 功能面小是刻意的——两遍的成本此时最低，返工也最便宜。

## 7. 测试策略（规划）

- `core` — 纯逻辑，单元测试覆盖 node 树操作（增删改、层级移动、z 序、坐标累加）。这是最该测的一层。
- `renderer-*` — **对照测试**：同一份 node 树喂给两个渲染器，断言产出的几何结果一致（位置、尺寸、层级）。这层测试的价值是「防止两个实现悄悄分叉」。
- **切换测试**（本项目特有，优先级高）：构造一份带选中与非默认视口的状态 → 切换渲染器 → 断言 node 树、选中集、视口三者不变，且旧渲染器的 DOM 与监听器已清空。这条测试直接守着 `AGENT.md` 的「状态不许渗进渲染器」禁止项。
- `apps/web` — 端到端只覆盖主路径（新建节点 / 拖动 / 发起生成 / 结果落回画布）。
- 选型结论所需的**性能对照**单独建 benchmark harness，不混进单测：同一份 node 树按 N=100/500/2000 节点压，量首屏渲染耗时、拖拽帧率、内存。**数字必须可复跑**，不接受一次性手测印象。
