## ~~选型结论已出：推荐 DOM~~（`architecture.md` §8.3）

两侧终于**同题跑过一次**（同为 `960×1300` 视口、8 个 460×260 节点、3 秒窗口、全部 muted）：

| 并发 | Leafer rAF | 长帧 | DOM rAF | 长帧 |
|---|---|---|---|---|
| 1 路 | 60.18 | 0 | 60.14 | 0 |
| 4 路 | **52.24** | 0 | 30.89 | 0 |
| 8 路 | 18.01 | **29** | **30.09** | **0** |

### 但理由不是帧率高 —— 4 路时 Leafer 是 DOM 的 1.7 倍

真正该看的是**「解码了多少帧、真正画出来多少帧」**：

| | 每路每秒解码 | 每路每秒上屏 | 丢失 |
|---|---|---|---|
| Leafer 4 路 | ~25 | ~50（同帧重绘） | **0** |
| Leafer 8 路 | ~27.5 | **~19** | **约 30%** |
| DOM（4/8 路） | ~25 | 合成器直接上屏 | **~0** |

**Leafer 的转折点在 4 路和 8 路之间。**

### 决定性的是失败模式不对等

| | 负载升高时会发生什么 |
|---|---|
| **Leafer** | **视频本身开始丢帧** —— 视频渲染与应用渲染是同一个循环 |
| **DOM** | **只有自绘 UI 变慢**，视频始终由合成器按原速上屏 |

对 AI 生成画布，这两者严重性差得很远：拖拽不跟手能忍，
**但生成出来的视频卡，会被直接理解成生成质量有问题**。

而且这是**架构性的**——只要视频要经过 `drawImage` 进画布，
应用渲染的任何压力都会转嫁到视频画面上，调优抹不平。

### 🔴 唯一还需要你判断的一项

**DOM 那 30fps 的拖拽手感能不能接受？机器测不出来，只能你亲手拖一遍。**
（Leafer 在 4 路以内的自绘 UI 明显更流畅，这是它真实的优势。）

### 🔴 因此产生一个要你定的决策

结论既然倾向 DOM，**Leafer 那一侧还继续投入吗？**

- **继续**：保持双实现，代价是每个功能都要做两遍
- **停掉**：省一半工作量，但失去「换回去」的退路，也失去持续的对照基准
- **冻结**：不再跟进新功能，但保留现有代码与探针，日后要比较随时能跑

我倾向**冻结**，但这属于范围调整，**我不替你定**。

内存两侧都是空白（页面级 API 测不到解码缓冲与显存）· 每档只跑一次、方差未知 ·

### 1. 🔴 「用现成方案 vs 继续自建」

**背景**：你观察到竞品基本都用 DOM，让我调研有没有开箱即用的。

## 四、值得你知道的技术判断

### 1. 五个设计空洞，全部在写代码之前被抓到

Codex 五次因「设计有缺口」停下上报，**每次都是真问题**：

1. `onNodeAction` 依赖了尚未存在的 `callbacks` 接口
2. 连线层序：「画在所有节点下方」没定义画布底色算哪层——**Kimi 实现时踩了，连线被白底整个盖住，而所有测试都是绿的**
3. 多选等比缩放缺 core 映射函数，且 `minSize` 从没钉过值
4. `remove-node` 的逆操作丢信息，撤销删除时连线恢复不回来
5. `InboundRef` 缺被引用目标 id，删 frame 时后代的引用无法无损恢复

**共同点：我写规格时下的每个「必然如此」的断言，都没有逐项验证。** 已在 `domain.md` 里记了一笔自嘲。

### 2. 一个 parity 测不出来的 bug，靠截图抓到

Kimi 把连线画在了画布底色下面，**完全不可见，但所有测试都绿**——因为连线不进 `getRenderedBounds()`，parity 摸不到它。它跑 Playwright 截图目视才发现。

**教训**：机器只能验它被告知要验的东西。

### 3. 🔴 刚抓到一个更危险的：测试存在但永远不跑

| `<style>` | 6,001 | 每个生成单元注入一份 → **收敛成 1 份共享样式表** |
| `<button>` | 18,011 | hover 才可见却全部预渲染 → **改为跟随 hover 的单例浮层** |
| `<video>` | 2,000 | 全部 `preload="metadata"` → 改 `none` |
| SVG | 71,104 | 连线层，占总量一半以上 → **靠视口裁剪** |

⚠️ **纠正我此前一个说法**：我说过「DOM 免费拿到视口外不合成的优化」——
**那只对绘制成立，对存在不成立**。浏览器跳过视口外元素的*绘制*，
但元素本身仍在 DOM 树里占内存、参与样式计算与布局。你实测的 2.4GB 就是这么来的。

### 🔴 中键平移抖动 —— 以及我查错两次的过程

| | 修复前 | 修复后 |
|---|---|---|
| 平均 | 23.81 ms（42.0 fps） | **17.14 ms（58.3 fps）** |
| 中位数 | 16.7 ms | 16.7 ms |
| **p95** | **50.0 ms** | **16.8 ms** |
| 最大 | 50.0 ms | 33.4 ms |

**1 万节点的画布现在平移起来和 10 个节点一样顺**（对照组：平均 16.75、p95 16.8、最大 33.3）。

**注意「平均 42fps」这个数有多误导**：中位数其实是满帧 16.7ms，
只有约 5% 的帧卡在 50ms —— 而**人眼对这种不均匀比对稳定低帧率敏感得多**。
只看平均会得出「还行」的错误结论。此后基准一律要报中位数与 p95。

**我在这件事上查错了两次**：
第一次读代码猜「连线层每帧重建」——对，但只是部分；
第二次看到「堆锯齿 + 长任务列表为空」就断定是 GC 主导，**方向错了** ——
我把一个歧义证据当成了排他证据（没有长任务也可能只是单帧恰好卡在 50ms 阈值边缘）。
最后是实测数据证明裁剪重算才是主因。

### 关于「Leafer 的交互不是走它自带的」

你观察得对，而且是有意为之：指针事件挂在外层 HTML，命中测试用 `core` 的纯函数，
Leafer 内建手势被主动关闭且有挂载时断言强制它保持关闭。

**理由是 parity** —— 若两侧各用自己的事件系统，行为会分叉，对照就失去意义。

**但代价是两侧都没跑在自己的天花板上**：DOM 本可白拿 `event.target`，
Leafer 本可用场景图拾取，现在统一走 O(N) 树遍历。

**你提的开关方案是对的**，已裁定并写进 `renderer-contract.md`：
空间查询可换（`unified` / `native`），业务过滤永远共用；
**且 dev 模式下两条路都跑、断言返回同一个 `fwId`** ——
一致性必须是被证明的，不是被假设的。
